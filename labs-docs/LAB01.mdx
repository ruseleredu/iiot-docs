Os laboratórios desta disciplina têm sempre a mesma forma. O grupo recebe um **repositório no
GitHub**, criado a partir de um _template_. Ali escreve o firmware do ESP32 no **VS Code** com o
**PlatformIO**, simula no **Wokwi** e entrega cada tarefa num **commit** `Tn:`. O autograder lê
esses commits. Mais adiante entram o broker MQTT, o Node-RED, o banco de dados e o CI, todos
rodando sobre as mesmas ferramentas.

Os Labs 01 e 02 preparam esse ambiente. O Lab 01 cuida do **Git** e do **GitHub**; o Lab 02, do
**PlatformIO**, do **Wokwi** e do **Docker**. Nesta aula:

1. você instala e confere as ferramentas;
2. o Git passa a saber **quem** você é, e o GitHub passa a aceitar os seus `push`;
3. o grupo pratica o fluxo que vai usar o semestre inteiro: _branch_, _pull request_, revisão e
   _merge_, inclusive quando dois mexem na mesma linha;
4. o `README.md` do grupo ganha **badges**, um **diagrama** e uma **fórmula**: os recursos de
   Markdown do GitHub que os relatórios dos próximos labs usam.

```mermaid
flowchart LR
  PC["seu computador<br/>VS Code + Git + gh"] -- "git push (branch)" --> GH["GitHub<br/>repositório do grupo"]
  GH -- "pull request<br/>revisão + merge" --> M["main"]
  M -- "git pull" --> PC
  GH -- "commits Tn:" --> AG["autograder"]
```

## Objetivos

- Instalar e **verificar** o ambiente: VS Code, Git, GitHub CLI e Python.
- Configurar a **identidade** do Git e autenticar o `gh`, sem guardar senha em lugar nenhum.
- Usar o fluxo de trabalho em grupo: `clone`, `commit`, `push`, `pull`, _branch_, _pull request_,
  revisão e _merge_.
- **Resolver um conflito** de merge sem perder o trabalho de ninguém.
- Escrever um `README.md` com **diagramas** (Mermaid), **expressões matemáticas** (LaTeX) e
  **badges** (Shields.io).

### 1.1 O terminal do VS Code é o Prompt de Comando

Os comandos desta disciplina são escritos para o **Prompt de Comando** (`cmd`). O PowerShell,
padrão do VS Code no Windows, trata aspas, `&&`, `>` e `%VARIAVEL%` de outro jeito, e um comando
copiado daqui pode falhar ou fazer outra coisa. Por isso, cada repositório tem o arquivo
`.vscode/settings.json`:

```json title=".vscode/settings.json"
{
  "terminal.integrated.defaultProfile.windows": "Command Prompt"
}
```

Crie o arquivo pelo VS Code (**Explorer** → nova pasta `.vscode` → novo arquivo
`settings.json`) depois de clonar o repositório (2.4), e abra um terminal novo (**Ctrl+Shift+`**).
O nome do terminal, à direita, tem de ser **cmd**, e o prompt fica assim:

```text title="Terminal do VS Code"
Microsoft Windows [versão 10.0.26100.xxxx]
(c) Microsoft Corporation. Todos os direitos reservados.

C:\Users\aluno\lab01-grupo-x>
```

:::note[Comentários no cmd]
No `cmd` não existe comentário com `#`: o texto seria passado ao comando. Nesta página, as
explicações estão fora dos blocos de comando, ou em linhas `rem`.
:::

## Parte 2 — Identidade, autenticação e clone {/* #parte-2 */}

### 2.1 Quem você é para o Git

Cada commit leva um **nome** e um **e-mail**. O GitHub usa o e-mail para ligar o commit à sua
conta: é assim que o autograder e o professor sabem **quem** fez o quê no grupo.

```shell title="Terminal (cmd)"
git config --global user.name "Seu Nome Completo"
git config --global user.email "12345678+seu-usuario@users.noreply.github.com"
git config --global init.defaultBranch main
git config --global pull.rebase false
git config --global core.autocrlf true
git config --global --list
```

O e-mail `...@users.noreply.github.com` está em **GitHub → Settings → Emails** ("Keep my email
address private"). Com ele, o seu e-mail pessoal não fica público no histórico do repositório.
O `pull.rebase false` faz o `git pull` juntar por _merge_ (o fluxo desta disciplina), e o
`core.autocrlf true` converte os fins de linha do Windows (CRLF) para LF no repositório, e o
inverso na sua pasta. O comando `git config --list --show-origin` da aba **Git SCM** mostra de
qual arquivo vem cada configuração.

### 2.2 O comando `git conferir`

Em todas as tarefas da disciplina, antes do commit `Tn:`, o roteiro manda conferir os arquivos
com `git conferir`. É um **alias** do Git (um comando que você mesmo cria), configurado uma vez:

```shell title="Terminal (cmd)"
git config --global alias.conferir "!f() { r=$(pwd -W 2>/dev/null || pwd); echo raiz do repositorio: $r; test -z $GIT_PREFIX || echo ATENCAO: o terminal esta em $GIT_PREFIX, fora da raiz. Antes do git add, rode: cd /d $r; test $# -eq 0 && return; for a in $@; do if [ -e $a ]; then echo ok $a; else echo FALTA $a; fi; done; echo == mudancas desde o ultimo commit:; git status --short --ignored -- $@; }; f"
```

Depois, `git conferir` seguido dos arquivos da tarefa, de qualquer pasta do repositório:

```text title="git conferir README.md evidencias/t1-ambiente.txt (exemplo)"
raiz do repositorio: C:/Users/aluno/lab01-grupo-x
ok README.md
FALTA evidencias/t1-ambiente.txt
== mudancas desde o ultimo commit:
 M README.md
```

| Na saída               | Quer dizer                                                                |
| ---------------------- | ------------------------------------------------------------------------- |
| `ATENCAO: o terminal…` | o terminal está numa subpasta: rode o `cd /d` indicado antes do `git add` |
| `FALTA`                | o arquivo não está nesse caminho (pasta errada, nome errado, `.txt.txt`)  |
| `??` / `M`             | arquivo novo / modificado: entra no commit                                |
| `!!`                   | bloqueado pelo `.gitignore`: o `git add` vai falhar                       |
| arquivo não aparece    | já está no Git e não mudou desde o último commit                          |

O Git roda o alias na **raiz** do repositório, mesmo que você esteja em `src\` ou
`evidencias\`, por isso os caminhos são sempre a partir da raiz e com `/`.

:::tip[Preveja antes de rodar]
**P1:** e se o `user.email` estiver errado (o e-mail do computador do laboratório, por
exemplo)? O commit é aceito pelo GitHub? O que aparece no lugar do seu avatar na lista de
commits, e o que isso significa para a **sua** nota num trabalho em grupo? Confira na T2.
:::

### 2.3 Autenticar o `gh`

O GitHub não aceita a senha da conta no `git push`. Quem autentica é o **GitHub CLI**: ele
abre o navegador, você autoriza, e ele passa a atender o Git como _credential helper_.

```shell title="Terminal (cmd)"
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh auth status
```

O `gh auth login` mostra um código de 8 caracteres e abre o navegador: cole o código e
autorize. O `gh auth setup-git` faz o `git push` usar esse login.

```text title="Saída esperada (trecho)"
github.com
  ✓ Logged in to github.com account seu-usuario (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
```

:::warning[Computador compartilhado]
No laboratório, o login fica guardado no computador até você sair. Antes de ir embora, faça o
**logout** do fim desta página. Quem usar a máquina depois teria acesso de escrita aos **seus**
repositórios.
:::

### 2.6 Registrar o ambiente


```text title="evidencias/t1-ambiente.txt (trecho; as versões variam)"
x64

Seu Nome Completo
12345678+seu-usuario@users.noreply.github.com
```

## Parte 3 — README e primeiro push {/* #parte-3 */}

### 3.1 O ciclo básico

```mermaid
sequenceDiagram
  participant W as pasta de trabalho
  participant S as staging (git add)
  participant L as repositório local
  participant R as GitHub (origin)
  W->>S: git add arquivo
  S->>L: git commit -m "Tn: ..."
  L->>R: git push
  R->>L: git pull (o que os outros enviaram)
  L->>W: (arquivos atualizados)
```

Antes de qualquer coisa: `git status`. Ele diz em que ramo você está, o que mudou e o que está
pronto para o commit. Use-o o tempo todo.

### 3.2 O `README.md` do grupo

Um integrante edita o `README.md`. Ele vai ser a capa de todos os repositórios da disciplina:

```markdown title="README.md"
# Lab 01 — Grupo X

## Integrantes

| Nome   | Usuário no GitHub |
| ------ | ----------------- |
| Nome 1 | @usuario1         |
| Nome 2 | @usuario2         |

## Previsões

- **P1:** ...
- **P2:** ...
- **P3:** ...
```

```shell title="Terminal (cmd)"
git status
git add README.md
git commit -m "T2: README com os integrantes"
git push
git log --oneline -3
```

Os **outros** integrantes trazem o commit para as suas máquinas. O commit `T2:` aparece no
`git log`:

```shell title="Terminal (cmd, cada um dos outros integrantes)"
git pull
git log --oneline -3
```

Abra o repositório no navegador (`gh repo view --web`), clique em **commits** e confira o P1: o
seu avatar aparece ao lado do commit?

:::note[Mensagens de commit nesta disciplina]
Cada tarefa entregue tem **um** commit cuja mensagem começa com `Tn:` (`T1:`, `T2:`…). O
autograder procura essas mensagens; vale o commit `Tn:` mais recente de cada tarefa. Commits
intermediários podem ter qualquer mensagem, desde que descritiva (`corrige pino do LED`, e não
`asdf`).
:::

## Parte 4 — Branch, pull request e conflito {/* #parte-4 */}

### 4.1 Por que não todo mundo direto na `main`?

Se todos fazem `push` na `main` ao mesmo tempo, um sobrescreve ou atrapalha o outro, e ninguém
revisa nada. O fluxo da disciplina é: **cada mudança num ramo** (_branch_) → **pull request**
(PR) → alguém do grupo **revisa** → **merge** na `main`.

```mermaid
gitGraph
  commit id: "T2: README"
  branch t3-ana
  commit id: "presença Ana"
  checkout main
  branch t3-bruno
  commit id: "presença Bruno"
  checkout main
  merge t3-ana id: "PR #1"
  checkout t3-bruno
  merge main id: "resolve conflito"
  checkout main
  merge t3-bruno id: "PR #2"
```

### 4.2 Cada integrante, no seu computador

**Todos ao mesmo tempo**, cada um no seu computador, partindo da `main` atualizada:

O `git switch -c` cria o ramo e muda para ele (troque `ana` pelo seu nome):

```shell title="Terminal (cmd, cada integrante)"
git switch main
git pull
git switch -c t3-ana
```

Crie (ou edite, se já existir no seu ramo) o arquivo `evidencias/t3-presenca.md` com **exatamente**
este conteúdo, trocando só a terceira linha:

```markdown title="evidencias/t3-presenca.md"
# Presença no Lab 01

Quem fez este arquivo: Ana (@usuario-da-ana)
```

O `-u` do primeiro `push` liga o ramo local ao remoto; nos seguintes, basta `git push`:

```shell title="Terminal (cmd)"
git add evidencias/t3-presenca.md
git commit -m "presença da Ana"
git push -u origin t3-ana
gh pr create --base main --title "Presença da Ana" --body "Lab 01, T3"
```

### 4.3 Revisar, juntar e resolver o conflito

1. Outro integrante abre o PR (`gh pr list` e `gh pr view 1 --web`), lê a mudança em **Files
   changed** e aprova (**Review changes → Approve**).
2. Quem abriu o PR faz o merge: `gh pr merge 1 --merge --delete-branch`.
3. O **segundo** PR agora mostra _This branch has conflicts that must be resolved_: os dois ramos
   mudaram a **mesma linha** do mesmo arquivo. O dono do segundo PR resolve:

```shell title="Terminal (cmd, dono do PR com conflito)"
git switch t3-bruno
git pull origin main
git status
```

O `git pull origin main` traz a `main` e avisa `CONFLICT (add/add)`. O `git status` mostra o
arquivo em **both added**: os dois ramos criaram o mesmo arquivo com conteúdos diferentes.

No VS Code, o arquivo aparece com as marcas do conflito:

```text title="evidencias/t3-presenca.md (durante o conflito)"
# Presença no Lab 01

<<<<<<< HEAD
Quem fez este arquivo: Bruno (@usuario-do-bruno)
=======
Quem fez este arquivo: Ana (@usuario-da-ana)
>>>>>>> 52f781f13aa312d984ce2e0dc6056b2a83372c98
```

Entre `<<<<<<< HEAD` e `=======` está a **sua** versão; entre `=======` e `>>>>>>>`, a que
veio da `main` (identificada pelo hash do commit).

Resolver é **editar o arquivo** até ele ficar como deve ser, sem as marcas, mantendo o trabalho
dos dois:

```markdown title="evidencias/t3-presenca.md (resolvido)"
# Presença no Lab 01

Quem fez este arquivo: Ana (@usuario-da-ana)
Quem fez este arquivo: Bruno (@usuario-do-bruno)
```

```shell title="Terminal (cmd)"
git add evidencias/t3-presenca.md
git commit -m "resolve conflito com a presença da Ana"
git push
```

O PR fica verde: revise, aprove e faça o merge como antes. Repita até o PR de **todos** os
integrantes estar na `main`.

:::tip[Preveja antes de rodar]
**P2:** se a Ana tivesse escrito na **linha 3** e o Bruno numa **linha 5** nova, haveria
conflito? Por que o Git consegue juntar sozinho mudanças em linhas diferentes, mas não na mesma
linha? E por que o `git push --force` "resolveria" o conflito do jeito errado?
:::

### 4.4 Evidência

Com todos os PRs juntados, um integrante atualiza a `main` e registra:

```shell title="Terminal (cmd)"
git switch main
git pull
(gh pr list --state merged & echo. & git log --oneline --graph -15) > evidencias\t3-prs.txt 2>&1
type evidencias\t3-prs.txt
git add evidencias/t3-prs.txt
git commit -m "T3: PRs de todos e conflito resolvido"
git push
```

## Parte 5 — Markdown avançado no GitHub {/* #parte-5 */}

O GitHub renderiza, além do Markdown comum, três recursos que os relatórios desta disciplina
usam o tempo todo: **diagramas**, **expressões matemáticas** e **badges**. Os três são texto
puro no arquivo: entram no Git, aparecem no `diff` do PR e são revisados como código.

### 5.1 Criando diagramas

- [GitHub Docs — Criar diagramas](https://docs.github.com/pt/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams)

Um bloco de código com a linguagem `mermaid` vira um diagrama. Um fluxograma simples:

````markdown title="README.md (trecho)"
```mermaid
graph TD;
    A-->B;
    A-->C;
    B-->D;
    C-->D;
```
````

O GitHub mostra:

```mermaid
graph TD;
    A-->B;
    A-->C;
    B-->D;
    C-->D;
```

O mesmo Mermaid desenha os outros diagramas desta página: `flowchart`, `sequenceDiagram` e
`gitGraph`. Os diagramas dos labs seguintes (circuitos MQTT, fluxos do Node-RED) vão para o
`README.md` assim.

### 5.2 Escrevendo expressões matemáticas

- [GitHub Docs — Escrever expressões matemáticas](https://docs.github.com/pt/get-started/writing-on-github/working-with-advanced-formatting/writing-mathematical-expressions)

O GitHub usa a sintaxe do **LaTeX** (renderizada pelo MathJax):

| Forma                                  | Uso                                                         |
| -------------------------------------- | ----------------------------------------------------------- |
| `$ ... $`                              | expressão **na linha** do texto                             |
| `$$ ... $$`                            | expressão em **bloco**, numa linha própria                  |
| bloco de código com a linguagem `math` | bloco, sem conflito com o resto do Markdown (`_`, `*`, `\`) |

Por exemplo, a **desigualdade de Cauchy-Schwarz**. O `\` no fim da linha do título força a
quebra de linha:

```markdown title="README.md (trecho)"
**The Cauchy-Schwarz Inequality**\
$$\left( \sum_{k=1}^n a_k b_k \right)^2 \leq \left( \sum_{k=1}^n a_k^2 \right) \left( \sum_{k=1}^n b_k^2 \right)$$
```

E uma conta que aparece no Lab 02: o resistor que limita a corrente do LED no GPIO2 (3,3 V,
LED vermelho com ~2 V, corrente de ~6 mA):

````markdown title="README.md (trecho)"
O resistor do LED vale $R = \frac{V_{CC} - V_F}{I_F}$:

```math
R = \frac{3{,}3\ \text{V} - 2{,}0\ \text{V}}{6\ \text{mA}} \approx 217\ \Omega \;\Rightarrow\; 220\ \Omega
```
````

### 5.3 Static Badge

- [Shields.io — Static Badge](https://shields.io/badges)

Um _badge_ é uma imagem gerada pela URL: `https://img.shields.io/badge/<rótulo>-<mensagem>-<cor>`.
No Markdown, entra como qualquer imagem (`![texto alternativo](url)`):

```markdown title="README.md (trecho)"
![Version](https://img.shields.io/badge/github-repo-blue?logo=github)
![LAB status](https://img.shields.io/badge/LAB_01-OK-green?logo=github)
![LAB status](https://img.shields.io/badge/LAB_01-OK-blue?logo=github)
![LAB status](https://img.shields.io/badge/LAB_01-TODO-red?logo=github)
```

![Version](https://img.shields.io/badge/github-repo-blue?logo=github)
![LAB status](https://img.shields.io/badge/LAB_01-OK-green?logo=github)
![LAB status](https://img.shields.io/badge/LAB_01-OK-blue?logo=github)
![LAB status](https://img.shields.io/badge/LAB_01-TODO-red?logo=github)

| Na URL       | Vira no badge                                                    |
| ------------ | ---------------------------------------------------------------- |
| `_`          | espaço (`LAB_01` → "LAB 01")                                     |
| `__`         | um `_`                                                           |
| `--`         | um `-` (um `-` sozinho separa rótulo, mensagem e cor)            |
| `%20`        | espaço                                                           |
| `?logo=...`  | o ícone de um serviço (`github`, `espressif`, `docker`, `mqtt`…) |
| `&style=...` | o estilo: `flat`, `flat-square`, `for-the-badge`…                |

Um badge **estático** mostra só o que está escrito na URL: o `LAB_01-OK` continua verde mesmo
que nada funcione. No Lab 11, o CI ganha um badge **dinâmico**, que muda de cor sozinho quando
o build quebra.

## Projeto integrador — README por issue e pull request {/* #integrador */}

Num projeto real, o trabalho começa por uma **issue** (o que precisa ser feito), segue num
**ramo** e termina num **PR que fecha a issue** quando entra na `main`. Aqui, a issue é deixar
o `README.md` do grupo com a cara dos relatórios da disciplina.

### Requisitos

1. **Issue.** Um integrante abre a issue:

   ```shell title="Terminal (cmd)"
   gh issue create --title "README com badges, diagrama e fórmula" --body "Badges no topo, diagrama Mermaid do fluxo do grupo e a fórmula do resistor do LED."
   gh issue list
   ```

   Anote o número da issue (ex.: `#3`).

2. **Ramo.** Crie o ramo `t4-readme` a partir da `main` atualizada:

   ```shell title="Terminal (cmd)"
   git switch main
   git pull
   git switch -c t4-readme
   ```

3. **`README.md`.** Acrescente, mantendo os integrantes e as previsões:
   - logo abaixo do título, **pelo menos dois badges**: um com o nome do grupo e um de status
     do Lab 01 (`TODO` em vermelho, por enquanto);
   - uma seção **Fluxo de trabalho** com um diagrama Mermaid (`flowchart` ou `gitGraph`) do
     caminho _issue_ → _branch_ → PR → revisão → _merge_ que o grupo usou;
   - uma seção **Fórmulas** com a conta do resistor do LED da Parte 5.2, em bloco.

   ```markdown title="README.md (início)"
   # Lab 01 — Grupo X

   ![Grupo](https://img.shields.io/badge/ELT85B-grupo_X-blue?logo=github)
   ![LAB status](https://img.shields.io/badge/LAB_01-TODO-red?logo=github)
   ```

4. **Conferir antes do PR.** Veja o resultado em dois lugares:
   - no VS Code, com o _preview_ do Markdown (**Ctrl+Shift+V**);
   - no GitHub, no próprio ramo:

   ```shell title="Terminal (cmd)"
   git add README.md
   git commit -m "README com badges, diagrama e fórmula"
   git push -u origin t4-readme
   gh repo view --web --branch t4-readme
   ```

   Corrija o que não renderizar (um `-` a mais no badge, uma `}` faltando na fórmula) e faça
   `git push` de novo. Quando estiver certo no GitHub, troque o badge do Lab 01 para
   `LAB_01-OK-green` e salve uma captura da página do ramo, com os badges, o diagrama e a
   fórmula, em `evidencias/t4-readme.png`.

5. **Commit e PR.**

   ```shell title="Terminal (cmd)"
   git add README.md evidencias/t4-readme.png
   git commit -m "T4: README com badges, diagrama e fórmula (closes #3)"
   git push
   gh pr create --base main --title "README com badges, diagrama e fórmula" --body "Closes #3"
   ```

6. **Revisão e merge.** Outro integrante revisa: em **Files changed**, o botão de _rich diff_
   (ícone de documento) mostra o README renderizado. Aprova e faz o merge. A issue **fecha
   sozinha** por causa do `Closes #3`. Confira com `gh issue list --state closed`.

7. **No `README.md`:** as respostas de P1, P2 e P3 (num PR, como todo o resto).

:::tip[Preveja antes de rodar]
**P3:** (a) o _preview_ do VS Code mostra a fórmula? E o diagrama Mermaid? E o GitHub mostra os
dois? Por que o mesmo arquivo `README.md` aparece diferente em cada lugar? (b) Os badges
aparecem com o computador **sem internet**? O que isso diz sobre onde a imagem é gerada? (c) Se
o firmware do Lab 02 parar de compilar, o badge `LAB_01-OK-green` muda de cor? Então, o que ele
garante para quem lê o README?
:::

## Referência rápida {/* #referencia */}

| Para…                                            | Comando                                                                 |
| ------------------------------------------------ | ----------------------------------------------------------------------- |
| Ver em que ramo estou e o que mudou              | `git status`                                                            |
| Conferir os arquivos de uma tarefa               | `git conferir <arquivos>` (2.2)                                         |
| Trazer o que os outros enviaram                  | `git pull`                                                              |
| Salvar e enviar                                  | `git add <arquivos>` → `git commit -m "msg"` → `git push`               |
| Criar um ramo e mudar para ele                   | `git switch -c nome`                                                    |
| Voltar para a `main` atualizada                  | `git switch main` → `git pull`                                          |
| Histórico resumido                               | `git log --oneline --graph -15`                                         |
| Abrir o repositório no navegador                 | `gh repo view --web` · num ramo: `gh repo view --web --branch nome`     |
| Abrir / listar / juntar PRs                      | `gh pr create` · `gh pr list` · `gh pr merge N --merge --delete-branch` |
| Issues                                           | `gh issue create` · `gh issue list`                                     |
| Desfazer mudanças **não** commitadas num arquivo | `git restore <arquivo>`                                                 |
| Preview do Markdown no VS Code                   | **Ctrl+Shift+V** (ou **Ctrl+K V**, ao lado)                             |

| Markdown no GitHub | Sintaxe                                                    |
| ------------------ | ---------------------------------------------------------- |
| Diagrama           | bloco de código com a linguagem `mermaid`                  |
| Fórmula na linha   | `$ ... $`                                                  |
| Fórmula em bloco   | `$$ ... $$` ou bloco de código com a linguagem `math`      |
| Badge estático     | `![alt](https://img.shields.io/badge/rótulo-mensagem-cor)` |

| Problema                                  | O que fazer                                                                                                                           |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `Permission denied` / `403` no `push`     | `gh auth status`; confira se você está no time do grupo; peça ao professor para conferir o acesso                                     |
| `Repository not found`                    | nome errado ou você ainda não é membro da organização: `gh repo view ELT85B-N21-2026-2/lab01-grupo-x`                                 |
| `rejected ... (fetch first)` no `push`    | alguém enviou antes: `git pull`, resolva o conflito se houver, e `git push` de novo. **Nunca** `--force`                              |
| Commit sem o seu avatar no GitHub         | `user.email` diferente do da conta (P1). Corrija o `git config` para os próximos commits                                              |
| `git: 'conferir' is not a git command`    | falta o alias (ou a configuração global foi apagada): rode de novo o comando da seção 2.2                                             |
| O terminal abre como **PowerShell**       | falta o `.vscode/settings.json` (1.1), ou a pasta aberta não é a raiz do repositório. Abra um terminal novo depois de criar o arquivo |
| Comando com `'aspas simples'` falha       | no `cmd`, só as **aspas duplas** agrupam um texto                                                                                     |
| Diagrama aparece como código no GitHub    | o bloco tem de começar com três crases e `mermaid`, e a sintaxe tem de estar certa: o GitHub mostra o erro no lugar do diagrama       |
| Fórmula aparece com `$` ou sem os índices | o Markdown comeu um `_` ou `\`: use o bloco com a linguagem `math`                                                                    |
| Badge quebrado ou com texto errado        | um `-` a mais na URL: no rótulo e na mensagem, `-` vira `--` e espaço vira `_`                                                        |
