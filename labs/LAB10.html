Laboratório 10

Checklist — SCADA da câmara com FUXA​

  • LAB IoT do lab10-x com a câmara, o fluxo do Lab 09 no Node-RED e os drivers do FUXA instalados (T1)
  • Três conexões no FUXA (OPC-UA, Modbus TCP e MQTT), em verde e com as tags lendo (T2)
  • Sinótico da câmara: estado em cores, valores, barra do aquecedor, setpoint e botões de modo (T3)
  • Dois alarmes, testados e reconhecidos (T4)
  • Histórico e tendência de T, SP e aquecedor (T5)
  • FUXA + Node-RED: o operador escolhe o controlador no FUXA, e um supervisor devolve a câmara ao PI interno se o Node-RED cair (T6)
  • Previsões P1–P4 respondidas no README.md
  • Nenhum push --force; cada tarefa num commit Tn:
  • Logout do Git e do gh no computador do laboratório
Pontuação

T1…T6 = 100 pts (esta aula não tem desafios): T1 10 · T2 20 · T3 20 · T4 15 · T5 15 · T6 20. O autograder normaliza para 0–10. Vale o commit Tn: mais recente de cada tarefa.

Nos Labs 08 e 09, o Node-RED fez o papel de SCADA: cada leitura, cada escala e cada botão foram programados em nós e funções. Funciona, mas não é assim que se supervisiona uma fábrica. Lá, o operador olha para um sinótico desenhado num software de SCADA/IHM, onde conexões, tags, alarmes e histórico são configurados, e não programados.

Nesta aula, você monta o SCADA da mesma câmara climática no FUXA, um SCADA web de código aberto que já vem no LAB IoT. Tudo o que você aprendeu nos Labs 08 e 09 reaparece, agora como configuração:

No Lab 08/09 (Node-RED)No FUXA
nó de configuração (modbus-client, OpcUa-Endpoint, mqtt-broker)conexão (Connection)
endereço lido por um nó (IR0, ns=2;s=Camara.temp, chave do JSON)tag
function "÷10"campo Divisor da tag
debug, ui-table, ui-chartsinótico, tendência
PI externo (Lab 09, T6)continua no Node-RED; o FUXA escolhe quem controla e vigia

Objetivos​

  • Configurar um SCADA: drivers, conexões e tags.
  • Comparar como cada protocolo é endereçado num SCADA: NodeId (OPC-UA), registrador base 1 com divisor (Modbus) e chave de JSON (MQTT).
  • Desenhar um sinótico: formas e cores ligadas ao estado, valores, barras e comandos.
  • Configurar alarmes com nível, texto e reconhecimento.
  • Registrar histórico e montar uma tendência.
  • (Integrador) Dividir o trabalho entre SCADA e controlador e implementar um supervisor de falha do controlador externo.

Material​

  • O LAB IoT do lab10-x (gerado pelo gen_iot_aluno.py, sem --sem-fuxa): mosquitto, Node-RED e FUXA.
  • O simulador camara-sim, na pasta camara-sim/ do repositório do grupo.
  • O fluxo do Lab 09 (nodered/flows-lab09.json, no repositório do Lab 09).
  • Acesso à internet no primeiro uso: os drivers do FUXA são baixados do npm.
FUXA: o que esta aula usa

O FUXA tem editor (/editor) e runtime (a tela do operador) no mesmo servidor. As conexões rodam no servidor, e não no navegador: 10 operadores com a tela aberta não multiplicam o tráfego com a câmara. A aula não usa usuários e permissões, relatórios, receitas nem o Node-RED embutido do FUXA. Também fica de fora o driver S7: ele não resolve nomes de host e exigiria o IP do contêiner.

Parte 3 — Sinótico da câmara​

Um sinótico mostra o processo, e não uma lista de números: o operador entende o estado da câmara num relance e age sem procurar.

3.1 Como um widget se liga a uma tag​

No editor, crie a tela Camara (painel Views ▸ ＋). Desenhe com as ferramentas de General e Controls. Com o objeto selecionado, Property (ou duplo clique) abre a ligação:

  • Tag: a variável que o widget mostra ou que dirige a animação;
  • Ranges: faixas de valor → cor (formas, botões) ou unidade e casas (valores);
  • Events: o que acontece no clique (Click ▸ Set Value).

Um alarme é uma condição anormal que exige ação do operador: tem prioridade, texto, instante de entrada e de saída e reconhecimento (ack). Em Setup ▸ Alarms ▸ ＋, escolha a tag e preencha o nível, a faixa min–max, o texto e o modo de reconhecimento.

Projeto integrador — FUXA + Node-RED: quem controla e quem vigia​

No Lab 09, o PI externo era ligado por um switch no dashboard do próprio Node-RED, e a P4 mostrou o problema: se o Node-RED cai com o aquecedor ligado, ninguém desliga. Agora as responsabilidades se separam:

QuemFaz
Câmaraexecuta: obedece ao modo (0 MANUAL, 1 ON/OFF, 2 PI interno)
Node-REDcontrola: roda o PI sempre que a câmara está em modo 0 e publica um sinal de vida
FUXAopera e vigia: o operador escolhe o modo; um script devolve a câmara ao modo 2 se o Node-RED parar

Requisitos​

  1. Node-RED: o PI obedece ao modo. Na function "PI" do Lab 09, troque o começo (a parte que olha o pi_ativo do switch):

    function: PI — início (o resto é igual ao Lab 09)
    // Lab 10: atua sempre que a câmara está em modo 0 (MANUAL), não importa quem escolheu
    // o modo (FUXA, dashboard, Modbus...). Fora do modo 0, fica parado.
    const p = msg.payload;
    if (p.modo !== 0) {
      context.set("I", 0);
      context.set("t0", null);
      node.status({
        fill: "grey",
        shape: "ring",
        text: `parado (modo ${p.modo})`,
      });
      return [null, null];
    }

  2. Node-RED: sinal de vida. Ligue a 2ª saída do PI (diagnóstico) a esta function e a um mqtt out elt85b/lab10/grupo-x/scada/pi:

    function: estado do PI -> SCADA
    // Estado do PI -> FUXA. O 'seq' é o sinal de vida que o supervisor do FUXA vigia.
    const seq = (context.get("seq") || 0) + 1;
    context.set("seq", seq);
    const p = msg.payload;
    msg.payload = {
      seq,
      e: Number(p.e.toFixed(3)),
      I: Number(p.I.toFixed(2)),
      aq: p.aq,
      ts: Date.now(),
    };
    return msg;

  3. FUXA: tags do PI. Na Broker MQTT, tópico elt85b/lab10/grupo-x/scada/pi, json, chaves seq (nome pi seq), e (pi erro) e aq (pi aquecedor). Mostre pi erro e pi aquecedor no sinótico, ao lado dos botões de modo.

  4. FUXA: supervisor. Em Setup ▸ Scripts ▸ ＋: nome supervisor_pi_externo, Execute mode Server, e em Script scheduling Loop with interval de 2 s:

    script: supervisor_pi_externo
    // Supervisor do PI externo: roda no SERVIDOR do FUXA a cada 2 s.
    // Se a câmara está em MANUAL (modo 0) e o Node-RED parou de publicar .../scada/pi
    // (o seq não muda há mais de 10 s), volta ao PI interno (modo 2) pelo Modbus.
    const LIMITE_S = 10;
    // tags pelo NOME (tag, conexão): os nomes têm de ser exatamente os da T2
    const MODO = $getTagId("modo", "Camara OPC-UA"); // leitura do modo
    const MODO_MB = $getTagId("HR1 modo", "Camara Modbus"); // escrita do fallback
    const SEQ = $getTagId("pi seq", "Broker MQTT"); // sinal de vida do Node-RED

    const modo = Number($getTag(MODO));
    const seq = $getTag(SEQ);
    const agora = Date.now();
    const wd =
      globalThis.wd ||
      (globalThis.wd = { seq: seq, desde: agora, modo: modo, disparou: false });
    // recomeça a contar quando chega seq novo OU quando o operador acabou de escolher o modo 0
    if (seq !== wd.seq || (modo === 0 && wd.modo !== 0)) {
      wd.seq = seq;
      wd.desde = agora;
      wd.disparou = false;
    }
    wd.modo = modo;
    const idade = Math.round((agora - wd.desde) / 1000);
    if (modo === 0 && idade > LIMITE_S && !wd.disparou) {
      wd.disparou = true; // uma vez só (a leitura do modo demora um ciclo)
      $setTag(MODO_MB, 2); // fallback: PI interno
      console.log(
        "supervisor: PI externo sem resposta ha " + idade + " s -> modo 2",
      );
    }

    O fallback escreve pelo Modbus de propósito: no log da câmara, opcua: modo = … é o operador e modbus: modo = 2 é o supervisor.
