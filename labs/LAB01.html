O Git é a ferramenta de gerenciamento de código-fonte mais utilizada por desenvolvedores profissionais.

  • O Git é um sistema de controle de versão distribuído gratuito e de código aberto, projetado para lidar com tudo, desde projetos pequenos até muito grandes, com rapidez e eficiência.
winget install --id Git.Git -e --source winget

Configurações do git:

git config --list --show-origin

O GitHub CLI traz o GitHub para o seu terminal.

  • O GitHub CLI é uma ferramenta de linha de comando que permite interagir com o GitHub diretamente pelo terminal. Está disponível para Windows, macOS e Linux.
winget install --id GitHub.cli -e --source winget

Status de login do GitHub CLI:

gh auth status

  • O Python pode ser instalado via winget:
winget install Python.Python.3.14

Verifique a versão instalada:

py --version && python --version && pip --version

Os laboratórios desta disciplina têm sempre a mesma forma. O grupo recebe um repositório no GitHub, criado a partir de um template. Ali escreve o firmware do ESP32 no VS Code com o PlatformIO, simula no Wokwi e entrega cada tarefa num commit Tn:. O autograder lê esses commits. Mais adiante entram o broker MQTT, o Node-RED, o banco de dados e o CI, todos rodando sobre as mesmas ferramentas.

Os Labs 01 e 02 preparam esse ambiente. Nesta aula:

  1. você instala e confere as ferramentas;
  2. o Git passa a saber quem você é, e o GitHub passa a aceitar os seus push;
  3. o grupo pratica o fluxo que vai usar o semestre inteiro: branch, pull request, revisão e merge, inclusive quando dois mexem na mesma linha;
  4. o PlatformIO faz o primeiro build. Ele baixa o toolchain do ESP32 (~300 MB), e é melhor que isso aconteça hoje, e não no meio do Lab 02.

Objetivos​

  • Instalar e verificar o ambiente: VS Code, Git, GitHub CLI, Python e as extensões PlatformIO e Wokwi.
  • Configurar a identidade do Git e autenticar o gh, sem guardar senha em lugar nenhum.
  • Usar o fluxo de trabalho em grupo: clone, commit, push, pull, branch, pull request, revisão e merge.
  • Resolver um conflito de merge sem perder o trabalho de ninguém.
  • Fazer o primeiro build do PlatformIO e saber o que vai (e o que não vai) para o repositório.

Material​

  • Computador com Windows 11 e ~5 GB livres. Todos os comandos desta página são para o Prompt de Comando (cmd), o terminal padrão do VS Code nesta disciplina.
  • Uma conta no GitHub, já aceita na organização da disciplina (ELT85B-N21-2026-2).
  • Nenhuma placa: os Labs 01 e 02 não precisam de ESP32 físico.

1.1 O terminal do VS Code é o Prompt de Comando​

Os comandos desta disciplina são escritos para o Prompt de Comando (cmd). O PowerShell, padrão do VS Code no Windows, trata aspas, &&, > e %VARIAVEL% de outro jeito, e um comando copiado daqui pode falhar ou fazer outra coisa. Por isso, cada repositório tem o arquivo .vscode/settings.json:

.vscode/settings.json
{
  "terminal.integrated.defaultProfile.windows": "Command Prompt"
}

Crie o arquivo pelo VS Code (Explorer → nova pasta .vscode → novo arquivo settings.json) depois de clonar o repositório (2.3), e abra um terminal novo (Ctrl+Shift+`). O nome do terminal, à direita, tem de ser cmd, e o prompt fica assim:

Terminal do VS Code
Microsoft Windows [versão 10.0.26100.xxxx]
(c) Microsoft Corporation. Todos os direitos reservados.

C:\Users\aluno\lab01-grupo-x>
Comentários no cmd

No cmd não existe comentário com #: o texto seria passado ao comando. Nesta página, as explicações estão fora dos blocos de comando, ou em linhas rem.

Parte 2 — Identidade, autenticação e clone​

2.1 Quem você é para o Git​

Cada commit leva um nome e um e-mail. O GitHub usa o e-mail para ligar o commit à sua conta: é assim que o autograder e o professor sabem quem fez o quê no grupo.

Terminal (cmd)
git config --global user.name "Seu Nome Completo"
git config --global user.email "12345678+seu-usuario@users.noreply.github.com"
git config --global init.defaultBranch main
git config --global pull.rebase false
git config --global core.autocrlf true
git config --global --list

O e-mail ...@users.noreply.github.com está em GitHub → Settings → Emails ("Keep my email address private"). Com ele, o seu e-mail pessoal não fica público no histórico do repositório. O pull.rebase false faz o git pull juntar por merge (o fluxo desta disciplina), e o core.autocrlf true converte os fins de linha do Windows (CRLF) para LF no repositório, e o inverso na sua pasta. O comando git config --list --show-origin da aba Git SCM mostra de qual arquivo vem cada configuração.

Preveja antes de rodar

P1: e se o user.email estiver errado (o e-mail do computador do laboratório, por exemplo)? O commit é aceito pelo GitHub? O que aparece no lugar do seu avatar na lista de commits, e o que isso significa para a sua nota num trabalho em grupo? Confira na T2.

2.2 Autenticar o gh​

O GitHub não aceita a senha da conta no git push. Quem autentica é o GitHub CLI: ele abre o navegador, você autoriza, e ele passa a atender o Git como credential helper.

Terminal (cmd)
gh auth login --hostname github.com --git-protocol https --web
gh auth setup-git
gh auth status

O gh auth login mostra um código de 8 caracteres e abre o navegador: cole o código e autorize. O gh auth setup-git faz o git push usar esse login.

Saída esperada (trecho)
github.com
  ✓ Logged in to github.com account seu-usuario (keyring)
  - Active account: true
  - Git operations protocol: https
  - Token: gho_************************************
Computador compartilhado

No laboratório, o login fica guardado no computador até você sair. Antes de ir embora, faça o logout do fim desta página. Quem usar a máquina depois teria acesso de escrita aos seus repositórios.

Parte 4 — Branch, pull request e conflito​

4.1 Por que não todo mundo direto na main?​

Se todos fazem push na main ao mesmo tempo, um sobrescreve ou atrapalha o outro, e ninguém revisa nada. O fluxo da disciplina é: cada mudança num ramo (branch) → pull request (PR) → alguém do grupo revisa → merge na main.

4.2 Cada integrante, no seu computador​

Todos ao mesmo tempo, cada um no seu computador, partindo da main atualizada:

O git switch -c cria o ramo e muda para ele (troque ana pelo seu nome):

Terminal (cmd, cada integrante)
git switch main
git pull
git switch -c t3-ana

Crie (ou edite, se já existir no seu ramo) o arquivo evidencias/t3-presenca.md com exatamente este conteúdo, trocando só a terceira linha:

evidencias/t3-presenca.md
# Presença no Lab 01

Quem fez este arquivo: Ana (@usuario-da-ana)

O -u do primeiro push liga o ramo local ao remoto; nos seguintes, basta git push:

Terminal (cmd)
git add evidencias/t3-presenca.md
git commit -m "presença da Ana"
git push -u origin t3-ana
gh pr create --base main --title "Presença da Ana" --body "Lab 01, T3"

4.3 Revisar, juntar e resolver o conflito​

  1. Outro integrante abre o PR (gh pr list e gh pr view 1 --web), lê a mudança em Files changed e aprova (Review changes → Approve).
  2. Quem abriu o PR faz o merge: gh pr merge 1 --merge --delete-branch.
  3. O segundo PR agora mostra This branch has conflicts that must be resolved: os dois ramos mudaram a mesma linha do mesmo arquivo. O dono do segundo PR resolve:
Terminal (cmd, dono do PR com conflito)
git switch t3-bruno
git pull origin main
git status

O git pull origin main traz a main e avisa CONFLICT (add/add). O git status mostra o arquivo em both added: os dois ramos criaram o mesmo arquivo com conteúdos diferentes.

No VS Code, o arquivo aparece com as marcas do conflito:

evidencias/t3-presenca.md (durante o conflito)
# Presença no Lab 01

<<<<<<< HEAD
Quem fez este arquivo: Bruno (@usuario-do-bruno)
=======
Quem fez este arquivo: Ana (@usuario-da-ana)
>>>>>>> 52f781f13aa312d984ce2e0dc6056b2a83372c98

Entre <<<<<<< HEAD e ======= está a sua versão; entre ======= e >>>>>>>, a que veio da main (identificada pelo hash do commit).

Resolver é editar o arquivo até ele ficar como deve ser, sem as marcas, mantendo o trabalho dos dois:

evidencias/t3-presenca.md (resolvido)
# Presença no Lab 01

Quem fez este arquivo: Ana (@usuario-da-ana)
Quem fez este arquivo: Bruno (@usuario-do-bruno)
Terminal (cmd)
git add evidencias/t3-presenca.md
git commit -m "resolve conflito com a presença da Ana"
git push

O PR fica verde: revise, aprove e faça o merge como antes. Repita até o PR de todos os integrantes estar na main.

Preveja antes de rodar

P2: se a Ana tivesse escrito na linha 3 e o Bruno numa linha 5 nova, haveria conflito? Por que o Git consegue juntar sozinho mudanças em linhas diferentes, mas não na mesma linha? E por que o git push --force "resolveria" o conflito do jeito errado?

Projeto integrador — primeiro build por issue e pull request​

Num projeto real, o trabalho começa por uma issue (o que precisa ser feito), segue num ramo e termina num PR que fecha a issue quando entra na main. Aqui, a issue é o primeiro build do firmware do ESP32.

Requisitos​

  1. Issue. Um integrante abre a issue:

    Terminal (cmd)
    gh issue create --title "Primeiro build do PlatformIO" --body "Criar o projeto esp32dev e compilar o pisca-LED."
    gh issue list

    Anote o número da issue (ex.: #3).

  2. Ramo e projeto. No ramo t4-build, crie o projeto PlatformIO na raiz do repositório (o pio funciona no terminal do VS Code depois do Path da aba PlatformIO):

    Terminal (cmd)
    git switch main
    git pull
    git switch -c t4-build
    pio project init -b esp32dev -O "framework=arduino" -O "monitor_speed=115200"

    O pio project init cria platformio.ini, src/, include/, lib/ e test/. Ele não apaga o README.md, as evidencias/ nem o .vscode/settings.json. (A aba PlatformIO mostra o mesmo comando com --ide vscode --sample-code: o primeiro gera arquivos de configuração do VS Code, o segundo um main.cpp de exemplo. Aqui você escreve o seu.)

  3. Pisca-LED. Crie src/main.cpp:

    src/main.cpp
    #include <Arduino.h>

    #define LED_PIN 2                     // GPIO2 (o LED do circuito do Lab 02)

    // Protótipo: em C/C++ uma função precisa ser declarada antes de ser usada
    void piscar(uint8_t pino, uint16_t meioPeriodoMs);

    void setup() {
      Serial.begin(115200);               // o mesmo valor do monitor_speed do platformio.ini
      pinMode(LED_PIN, OUTPUT);
      Serial.println("ESP32 inicializado! Lab 01, grupo X");
    }

    void loop() {
      piscar(LED_PIN, 500);
    }

    void piscar(uint8_t pino, uint16_t meioPeriodoMs) {
      digitalWrite(pino, HIGH);
      delay(meioPeriodoMs);
      digitalWrite(pino, LOW);
      delay(meioPeriodoMs);
    }

  4. Build. O primeiro build baixa a plataforma espressif32, o toolchain Xtensa e o core Arduino (~300 MB). Pode levar de 5 a 15 minutos. Os seguintes levam segundos. Rode o primeiro na tela, para acompanhar o download, e o segundo gravando a evidência:

    ========================= [SUCCESS] Took 41.27 seconds =========================

  5. O que vai para o repositório. git status mostra a pasta .pio/? Não deveria: o .gitignore do template a ignora. Confira e faça o commit só do que é código e configuração:

    Terminal (cmd)
    git status
    git add platformio.ini src include lib test evidencias/t4-build.txt
    git commit -m "T4: primeiro build do PlatformIO (closes #3)"
    git push -u origin t4-build
    gh pr create --base main --title "Primeiro build do PlatformIO" --body "Closes #3"

  6. Revisão e merge. Outro integrante revisa (o platformio.ini e o main.cpp fazem sentido?), aprova e faz o merge. A issue fecha sozinha por causa do Closes #3. Confira com gh issue list --state closed.

  7. No README.md: as respostas de P1, P2 e P3 (num PR, como todo o resto).
