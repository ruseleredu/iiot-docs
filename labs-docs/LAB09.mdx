No **Lab 08**, a câmara simulada apareceu pelos quatro protocolos, com o mínimo: um nó que lê
e um _inject_ que escreve. Você viu os **conceitos**: registradores e escala no Modbus, bytes e
tipos no S7, nós com nome e assinatura no OPC-UA.

Agora o Node-RED faz o papel de um **SCADA** de verdade:

1. lê **todo** o mapa de cada protocolo, com os truques que aparecem em equipamentos reais
   (_float_ em dois registradores, bits empacotados, Modbus RTU);
2. junta as leituras e mostra **a mesma câmara por cinco caminhos** num painel;
3. por fim, **assume o controle**: mede pelo OPC-UA, calcula um PI e atua pelo Modbus, e o
   SQLite registra tudo para comparar com o PI que roda dentro do "equipamento".

```mermaid

  subgraph SIM["camara-sim · lab09-x-camara"]
    PL[Planta térmica<br/>T · UR · aquecedor · ventilador]
  end
  PL ---|Modbus TCP · 502| NR
  PL ---|Modbus RTU sobre TCP · 5021| NR
  PL ---|S7 · 102 · DB1| NR
  PL ---|OPC-UA · 4840 · ns=2| NR
  PL -->|MQTT · telemetria| BRK[(mosquitto)] --> NR[Node-RED]
  NR -->|INSERT / SELECT| DB[(SQLite)]
  NR --> DSH[Dashboard /lab09]
```

## Objetivos

- Ler o **mapa completo** de um equipamento Modbus: escala, _float32_ em dois registradores
  (e a ordem das palavras), bits empacotados e entradas discretas, por **TCP** e por **RTU**.
- Montar a **tabela de variáveis** de um CLP S7 e tratar os `REAL`.
- Assinar **várias** variáveis OPC-UA e juntar as notificações, que chegam em **lotes**.
- Montar um **painel** com a mesma planta vista por cinco caminhos e escrever por qualquer um.
- (Integrador) Fechar uma **malha de controle PI no SCADA** e comparar com o PI embarcado,
  usando o **SQLite**.

## Parte 2 — Modbus completo {/* #parte-2 */}

### 2.1 O mapa inteiro

No Lab 08, você leu os IR 0 a 4. Este é o mapa completo da câmara (unit 1, endereços base 0):

| Tabela (código de função)                     | Acesso      | End.      | Variável                                                      |
| --------------------------------------------- | ----------- | --------- | ------------------------------------------------------------- |
| Coils (FC1 lê · FC5/FC15 escreve)             | R/W bit     | 0 / 1     | `habilitado` / `falha_dht` (simulação)                        |
| Discrete inputs (FC2)                         | R bit       | 0–4       | LED verde, amarelo, vermelho, `dht_ok`, alarme ativo          |
| Holding registers (FC3 lê · FC6/FC16 escreve) | R/W 16 bits | 0 / 1 / 2 | `habilitado` / `modo` (0 MANUAL, 1 ON/OFF, 2 PI) / `fonte_sp` |
|                                               |             | 3         | `setpoint` × 10 (350 = 35,0 °C)                               |
|                                               |             | 4 / 5     | `aquecedor_cmd` / `ventilador_cmd` (%), valem no modo MANUAL  |
| Input registers (FC4)                         | R 16 bits   | 0 / 1 / 2 | temperatura × 10 / umidade × 10 / setpoint efetivo × 10       |
|                                               |             | 3 / 4 / 5 | aquecedor / ventilador aplicados (%) / `pot_raw`              |
|                                               |             | 6 / 7     | `estado` (0 DESLIGADO … 4 ALARME) / `alarme` (bits)           |
|                                               |             | 8         | LEDs: bit0 verde, bit1 amarelo, bit2 vermelho                 |
|                                               |             | 10        | `heartbeat` (conta a cada ciclo do "firmware")                |
|                                               |             | 12–13     | temperatura em **float32** (palavra alta primeiro, ABCD)      |
|                                               |             | 14–15     | umidade em **float32** (ABCD)                                 |

Além da **escala** (Lab 08), dois truques que aparecem em quase todo equipamento real:

- **Float32 em dois registradores:** o mesmo valor aparece como `float` IEEE 754 ocupando
  **dois** registradores. A ordem das palavras (ABCD, CDAB…) muda de fabricante para
  fabricante, e errar a ordem dá números absurdos.
- **Bits empacotados:** vários sinais booleanos dentro de um registrador (o IR8 dos LEDs).

### 2.2 Dois clientes: TCP e RTU sobre TCP

O mesmo escravo responde em **duas** portas. A 502 usa **Modbus TCP** (cabeçalho MBAP, sem
CRC). A 5021 usa o quadro **RTU** (endereço + função + dados + **CRC-16**), o mesmo da RS-485,
só que transportado por TCP, como faz um conversor serial-Ethernet. Crie um segundo
**modbus-client**:

| Campo    | `câmara Modbus TCP` (do Lab 08) | `câmara Modbus RTU/TCP` (novo) |
| -------- | ------------------------------- | ------------------------------ |
| Type     | TCP                             | TCP                            |
| Host     | `lab09-x-camara`                | `lab09-x-camara`               |
| Port     | `502`                           | `5021`                         |
| TCP Type | **DEFAULT**                     | **TELNET**                     |
| Unit-Id  | `1`                             | `1`                            |

:::warning[TELNET, não RTU-BUFFERED]
No `node-red-contrib-modbus`, o tipo que envia quadros **RTU crus** pelo socket se chama
**TELNET**. O "TCP-RTU-BUFFERED", apesar do nome, envia cabeçalho Modbus TCP, e o simulador na
5021 não responde (o nó fica em _timeout_).
:::

### 2.3 Ler e decodificar tudo

```mermaid
flowchart LR
  R1[modbus-read FC4 IR 0..17 · 2 s · topic modbus_tcp] --> DEC[function: decodifica IR]
  R2[modbus-read FC4 IR 0..17 · RTU · 5 s · topic modbus_rtu] --> DEC
  DEC --> DBG[debug Modbus TCP]
  R3[modbus-read FC2 DI 0..4 · 5 s] --> DBG2[debug LEDs/alarme]
```

- Troque o **modbus-read** do Lab 08 para Address `0`, Quantity **`18`**, Topic `modbus_tcp`,
  e o nome para "FC4 IR 0..17".
- Um segundo **modbus-read**, pelo cliente RTU, a cada `5 s`, Topic `modbus_rtu`.
- **modbus-read** "FC2 DI 0..4": _FC 2: Read Discrete Inputs_, Address `0`, Quantity `5`,
  direto num **debug** "LEDs/alarme (bits)".
- A function "÷10 e nomes" do Lab 08 vira esta:

```js title="function: decodifica IR"
// Input registers 0..17 da câmara -> objeto com nomes e unidades
const r = msg.payload;
if (!Array.isArray(r) || r.length < 18) return null;
const s16 = (v) => (v > 0x7fff ? v - 0x10000 : v); // int16 com sinal
const f32 = (i) => {
  // float32 big-endian (ABCD)
  const b = Buffer.alloc(4);
  b.writeUInt16BE(r[i], 0);
  b.writeUInt16BE(r[i + 1], 2);
  return b.readFloatBE(0);
};
const ESTADOS = ["DESLIGADO", "AQUECENDO", "RESFRIANDO", "ESTAVEL", "ALARME"];
msg.payload = {
  temp_x10: s16(r[0]) / 10, // IR0: °C x 10
  temp: Number(f32(12).toFixed(2)), // IR12-13: float32
  umid: Number(f32(14).toFixed(1)), // IR14-15
  sp_efetivo: s16(r[2]) / 10, // IR2
  aquecedor_pwm: r[3],
  ventilador_pwm: r[4],
  pot_raw: r[5],
  estado: r[6],
  estado_txt: ESTADOS[r[6]] ?? "?",
  alarme: r[7],
  leds: {
    verde: r[8] & 1,
    amarelo: (r[8] >> 1) & 1,
    vermelho: (r[8] >> 2) & 1,
  },
  heartbeat: r[10],
};
return msg;
```

Ligue a function a um **debug** "Modbus TCP" (_status_: `payload.temp`). As leituras TCP e RTU
caem no **mesmo** debug: o `msg.topic` (`modbus_tcp` ou `modbus_rtu`) diz de onde veio cada uma.

```text title="Debug (trecho)"
Modbus TCP:          { temp_x10: 34.8, temp: 34.8, umid: 37.8, sp_efetivo: 35, aquecedor_pwm: 0,
                       ventilador_pwm: 20, pot_raw: 1758, estado: 3, estado_txt: 'ESTAVEL', alarme: 0,
                       leds: { verde: 1, amarelo: 0, vermelho: 0 }, heartbeat: 152 }
LEDs/alarme (bits):  [ true, false, false, true, false, false, false, false ]
```

As entradas discretas chegam como **8** booleanos, embora você tenha pedido 5: o Modbus
transporta bits em **bytes** inteiros. Só os 5 primeiros têm significado (verde, amarelo,
vermelho, `dht_ok`, alarme).

:::tip[Preveja antes de rodar]
**P1:** (a) com 36,2 °C, os IR12–13 valem `0x4210` e `0xCCCD`. Se o seu cliente lesse na
ordem **CDAB** (palavra baixa primeiro), que número apareceria? Troque `r[i]` e `r[i + 1]` na
`f32` e confira. Que tipo de valor denuncia uma ordem de palavras errada? (b) O IR8 vale `6`.
Quais LEDs estão acesos? Se o equipamento já entrega os LEDs nos DI 0–2, por que também os
empacota no IR8?
:::

## Parte 3 — S7 completo {/* #parte-3 */}

### 3.1 A tabela de variáveis inteira

| Endereço nodes7         | Bytes | Variável                                   | Acesso |
| ----------------------- | ----- | ------------------------------------------ | ------ |
| `DB1,X0.0`              | 0.0   | `habilitado`                               | R/W    |
| `DB1,X0.1`              | 0.1   | `fonte_sp` (0 remoto, 1 potenciômetro)     | R/W    |
| `DB1,INT2`              | 2–3   | `modo`                                     | R/W    |
| `DB1,REAL4`             | 4–7   | `setpoint` (°C)                            | R/W    |
| `DB1,REAL8`             | 8–11  | `aquecedor_cmd` (%)                        | R/W    |
| `DB1,REAL12`            | 12–15 | `ventilador_cmd` (%)                       | R/W    |
| `DB1,REAL20`            | 20–23 | `temp` (°C)                                | R      |
| `DB1,REAL24`            | 24–27 | `umid` (%)                                 | R      |
| `DB1,REAL28`            | 28–31 | `sp_efetivo` (°C)                          | R      |
| `DB1,REAL32` / `REAL36` | 32–39 | `aquecedor_pwm` / `ventilador_pwm` (%)     | R      |
| `DB1,INT40` / `INT42`   | 40–43 | `estado` / `alarme`                        | R      |
| `DB1,X44.0` … `X44.2`   | 44    | `led_verde`, `led_amarelo`, `led_vermelho` | R      |
| `DB1,DINT48`            | 48–51 | `heartbeat`                                | R      |

O DB1 do simulador é **sem acesso otimizado**: os endereços são fixos, como num S7-300 ou num
S7-1200 com _Optimized block access_ desligado. Num S7-1200/1500 real, isso e o _PUT/GET_
precisam ser liberados no TIA Portal.

### 3.2 Ler, arredondar e escrever o modo

No **s7 endpoint** "câmara S7 (DB1)", complete a tabela com as **15** variáveis (o nome à
direita, o endereço à esquerda), com os nomes exatamente como na coluna "Variável".

```mermaid
flowchart LR
  IN[s7 in · All variables] --> F[function: arredonda · topic s7] --> D[debug S7]
  I1[inject SP 33 / 43] --> O1[s7 out · setpoint]
  I2[inject modo 1 / 2] --> O2[s7 out · modo]
```

Entre o **s7 in** e o debug, uma function que arredonda os `REAL` (no Lab 08 eles chegavam como
`36.400001525878906`) e marca a origem:

```js title="function: arredonda"
// "s7 in" (todas as variáveis) -> números arredondados
const p = msg.payload;
const r = (v) => Math.round(v * 100) / 100;
msg.payload = Object.assign({}, p, {
  temp: r(p.temp),
  umid: r(p.umid),
  setpoint: r(p.setpoint),
  sp_efetivo: r(p.sp_efetivo),
  aquecedor_pwm: r(p.aquecedor_pwm),
  ventilador_pwm: r(p.ventilador_pwm),
});
msg.topic = "s7";
return msg;
```

E um **s7 out** _Variable_ `modo`, com injects `1` (ON/OFF) e `2` (PI). Escreva `2` e confira,
no debug "Modbus TCP", que o comportamento do aquecedor muda: o ON/OFF liga e desliga a 100 %,
o PI modula.

```text title="Debug S7"
{ habilitado: true, fonte_sp: false, modo: 1, setpoint: 35, temp: 34.9, umid: 37.9, sp_efetivo: 35,
  aquecedor_pwm: 0, ventilador_pwm: 20, estado: 3, alarme: 0, led_verde: true, led_amarelo: false,
  led_vermelho: false, heartbeat: 149 }
```

:::tip[Preveja antes de rodar]
**P2:** a mesma informação dos LEDs aparece de **três** formas: os DI 0–2 do Modbus (3 bits), o
IR8 (um registrador com 3 bits dentro) e os `DB1,X44.0…X44.2` do S7 (3 bits do mesmo byte).
Quantas **requisições** cada cliente precisa para ler os 3 LEDs **e** a temperatura? Por que o
**s7 in** "All variables" lê 15 variáveis sem fazer 15 requisições?
:::

## Parte 4 — OPC-UA em conjunto {/* #parte-4 */}

No Lab 08, você assinou `temp` e `setpoint`, cada um com um inject. Para um painel, é preciso
assinar **várias** variáveis e trabalhar com elas como **um** objeto.

```text title="Objects/Camara  (namespace urn:utfpr:camara-climatica = ns=2)"
Medicoes/    temp · umid · pot_raw                       ns=2;s=Camara.temp ...
Atuadores/   aquecedor_pwm · ventilador_pwm · *_duty
Estado/      estado · estado_txt · alarme · led_* · heartbeat · uptime · oled
Comandos/    habilitado · modo · fonte_sp · setpoint · aquecedor_cmd · ventilador_cmd   (graváveis)
Simulacao/   pot_raw_sim · falha_dht                                                     (graváveis)
```

```mermaid
flowchart LR
  I[inject assinar · once 4 s] --> L[function: lista de NodeIds · 9 msgs] --> C[OpcUa-Client · SUBSCRIBE · 2 s]
  C --> J[function: junta variáveis] --> D[debug OPC-UA]
  I2[inject SP 35] --> IT1[OpcUa-Item Camara.setpoint · Double] --> W[OpcUa-Client · WRITE]
  I3[inject modo 2] --> IT2[OpcUa-Item Camara.modo · Int32] --> W
```

### 4.1 Assinar nove variáveis

Troque os dois injects do Lab 08 por **um** inject "assinar" (_once_, 4 s) e uma function que
gera **uma mensagem por variável**, cada uma com o NodeId no `topic`:

```js title="function: lista de NodeIds"
// Uma mensagem por variável a assinar: msg.topic = NodeId, msg.datatype = tipo OPC-UA
const vars = {
  temp: "Double",
  umid: "Double",
  setpoint: "Double",
  sp_efetivo: "Double",
  aquecedor_pwm: "Double",
  ventilador_pwm: "Double",
  modo: "Int32",
  estado_txt: "String",
  heartbeat: "Int32",
};
return [
  Object.entries(vars).map(([n, t]) => ({
    topic: `ns=2;s=Camara.${n}`,
    datatype: t,
    payload: "",
  })),
];
```

Retornar `[ [msg1, msg2, …] ]` (um array **dentro** de outro) faz a function enviar as nove
mensagens em sequência pela mesma saída.

### 4.2 Juntar as notificações

Cada mudança chega numa mensagem separada (o NodeId no `topic`, o valor no `payload`). Entre o
OpcUa-Client e o debug, esta function guarda o último valor de cada variável e emite **um**
objeto:

```js title="function: junta variáveis"
// Cada variável assinada chega numa mensagem separada (msg.topic = NodeId).
// O servidor entrega as mudanças em LOTES (a cada ~2 s): guarda o último valor de
// cada variável e emite UM conjunto 200 ms depois da última mensagem do lote.
const nome = String(msg.topic).split("Camara.")[1];
if (!nome) return null; // ex.: a mensagem "subscriptionId"
const v =
  msg.payload && msg.payload.value !== undefined
    ? msg.payload.value.value // versões antigas do node-red-contrib-opcua
    : msg.payload;
const d = context.get("d") || {};
d[nome] = v;
context.set("d", d);
if (Object.keys(d).length < 9) return null; // ainda faltam variáveis
clearTimeout(context.get("tmr"));
context.set(
  "tmr",
  setTimeout(() => {
    const r = (x) => Math.round(x * 100) / 100;
    node.send({
      topic: "opcua",
      payload: Object.assign({}, d, {
        temp: r(d.temp),
        umid: r(d.umid),
        aquecedor_pwm: r(d.aquecedor_pwm),
        ventilador_pwm: r(d.ventilador_pwm),
      }),
    });
  }, 200),
);
return null;
```

```text title="Debug OPC-UA"
{ temp: 34.9, umid: 37.9, setpoint: 35, sp_efetivo: 35, aquecedor_pwm: 0, ventilador_pwm: 20,
  modo: 1, estado_txt: 'ESTAVEL', heartbeat: 149 }
```

:::warning[Por que o atraso de 200 ms?]
O servidor guarda **todas** as mudanças de cada item monitorado e as entrega juntas, a cada
2 s. O `heartbeat` muda a cada ciclo do simulador: chegam 4 ou 5 mensagens dele no mesmo
milissegundo. Emitir a cada mensagem geraria **4 ou 5 conjuntos repetidos** a cada 2 s (e 4 ou
5 linhas por ciclo no SQLite da T6). O `setTimeout` reiniciado a cada mensagem (_debounce_)
espera o lote terminar e emite **um** conjunto, com os valores mais recentes.
:::

## Projeto integrador — PI no Node-RED × PI interno {/* #integrador */}

Até aqui, quem controla a temperatura é o "firmware" da câmara (modo 1 ON/OFF ou modo 2 PI).
Agora o **SCADA assume o controle**: a câmara vai para o modo **0 MANUAL**, em que obedece aos
registradores **HR4** (aquecedor) e **HR5** (ventilador), e o Node-RED calcula esses valores
com um **PI**. A medição vem pelo **OPC-UA** e a atuação vai pelo **Modbus**, como num sistema
real em que o SCADA conversa com equipamentos de fabricantes diferentes.

```mermaid
flowchart LR
  SP[setpoint] --> E((e = SP − T))
  E --> PI[PI no Node-RED<br/>Kp = 12 · Ki = 0,4]
  PI -->|FC16 HR4..5 · Modbus| PL[câmara<br/>modo MANUAL]
  PL -->|T · assinatura OPC-UA · 2 s| E
  PL -->|INSERT a cada conjunto| DB[(SQLite · controle)]
```

O controlador é discreto, executado a cada conjunto do OPC-UA (~2 s):

```text title="PI com anti-windup"
e  = SP − T                              (°C)
I  = I + Ki · e · dt                     só se a saída não estiver saturada no sentido do erro
u  = Kp · e + I       → aquecedor = u limitado a 0…100 %
ventilador = 20 + 30 · (−e − 0,5)        limitado a 20…100 %  (20 % = circulação)
```

### Requisitos

1. **Ativação.** Um **ui-switch** "PI no Node-RED (modo MANUAL)" ligado a uma function de 2
   saídas:
   - **ligado:** guarda `flow.pi_ativo = true` e escreve `[1, 0]` em **HR0..1** (habilitado,
     modo MANUAL) com **FC16**;
   - **desligado:** escreve `2` no **HR1** com FC6 (volta ao PI interno).

   ```js title="function: ativa / desativa"
   // Liga/desliga o controle externo.
   // Ligar: HR0..1 = [1, 0]  -> habilitado, modo MANUAL (a câmara obedece HR4/HR5)
   // Desligar: HR1 = 2       -> volta ao PI interno
   flow.set("pi_ativo", msg.payload === true);
   node.status({
     fill: msg.payload ? "green" : "grey",
     shape: "ring",
     text: msg.payload ? "externo" : "interno",
   });
   return msg.payload ? [{ payload: [1, 0] }, null] : [null, { payload: 2 }];
   ```

2. **Controlador.** Function "PI" alimentada pelo **"junta variáveis"** da T4, com 2 saídas:
   `[aquecedor, ventilador]` para um **modbus-write** **FC16** em **HR4**, quantidade 2, e um
   objeto de diagnóstico para um debug. Ela só atua com `pi_ativo` **e** `modo === 0`. Fora
   disso, zera o integrador.

   ```js title="function: PI (Kp=12, Ki=0,4)"
   // Controlador PI EXTERNO. Entrada: conjunto do OPC-UA (a cada ~2 s).
   // Só atua quando o controle externo está ativo e a câmara está em modo MANUAL (0).
   const p = msg.payload;
   const ativo = flow.get("pi_ativo") === true;
   if (!ativo || p.modo !== 0) {
     context.set("I", 0);
     context.set("t0", null);
     return [null, null];
   }

   const KP = 12,
     KI = 0.4; // %/°C e %/(°C·s)  <-- ajuste aqui
   const agora = Date.now() / 1000;
   const t0 = context.get("t0");
   const dt = t0 ? Math.min(agora - t0, 10) : 0;
   context.set("t0", agora);

   const e = p.setpoint - p.temp; // erro (°C)
   let I = context.get("I") || 0;
   let u = KP * e + I;
   // anti-windup: só integra se não estiver saturado no sentido do erro
   if ((u < 100 || e < 0) && (u > 0 || e > 0))
     I = Math.min(100, Math.max(0, I + KI * e * dt));
   context.set("I", I);
   const aq = Math.round(Math.min(100, Math.max(0, KP * e + I)));
   const ve = Math.round(Math.min(100, Math.max(20, 20 + 30 * (-e - 0.5)))); // 20 % = circulação

   node.status({
     fill: "green",
     shape: "dot",
     text: `e=${e.toFixed(2)} I=${I.toFixed(1)} aq=${aq}% ve=${ve}%`,
   });
   return [{ payload: [aq, ve] }, { payload: { e, I, aq, ve } }];
   ```

   :::warning[FC16 no modbus-write]
   Para escrever **dois** registradores, o _FC_ do modbus-write tem de ser **FC 16: Preset
   Multiple Registers** (no fluxo exportado, `"dataType": "MHoldingRegisters"`) e o payload,
   um **array**. Com _FC 6_ e quantidade 2, o nó escreve **só o primeiro** valor e não dá
   erro: o ventilador nunca muda e o modo nunca vai a 0.
   :::

3. **Registro.** Tabela `controle` no **`/data/sqlite/lab09.sqlite`**: um nó de configuração
   **sqlitedb** com esse caminho (modo _Read-Write-Create_), um nó **sqlite** "consultas" em
   _Via msg.topic_ e um inject _once_ (0,5 s) com o `CREATE` no **topic**. Uma linha **por
   conjunto do OPC-UA**:

   ```sql title="msg.topic do inject 'Criar tabela'"
   CREATE TABLE IF NOT EXISTS controle (
       id          INTEGER PRIMARY KEY AUTOINCREMENT,
       recebido_em TEXT DEFAULT (strftime('%Y-%m-%d %H:%M:%f', 'now', 'localtime')),
       modo        INTEGER,   -- 0 MANUAL (PI no Node-RED), 1 ON/OFF, 2 PI interno
       t           REAL,      -- °C (OPC-UA)
       sp          REAL,      -- setpoint efetivo (°C)
       aq          REAL,      -- % aquecedor aplicado
       ve          REAL       -- % ventilador aplicado
   );
   ```

   ```js title="function: monta parâmetros"
   // Cada conjunto do OPC-UA -> uma linha (com parâmetros)
   const p = msg.payload;
   if (typeof p.temp !== "number" || typeof p.sp_efetivo !== "number")
     return null;
   msg.params = {
     $modo: p.modo,
     $t: p.temp,
     $sp: p.sp_efetivo,
     $aq: p.aquecedor_pwm,
     $ve: p.ventilador_pwm,
   };
   return msg;
   ```

   ```sql title="sqlite 'INSERT' (Prepared Statement)"
   INSERT INTO controle (modo, t, sp, aq, ve) VALUES ($modo, $t, $sp, $aq, $ve);
   ```

   4. rode as duas consultas abaixo (cada uma num inject com a consulta no **topic**, ligado ao
      nó "consultas" e a um debug "resultado").

   ```sql title="Comparar controladores (10 min)"
   SELECT CASE modo WHEN 0 THEN 'PI Node-RED' WHEN 1 THEN 'ON/OFF interno'
                    WHEN 2 THEN 'PI interno' END AS controlador,
          COUNT(*)                                             AS n,
          ROUND(AVG(ABS(sp - t)), 2)                           AS erro_medio,
          ROUND(100.0 * SUM(ABS(sp - t) > 0.5) / COUNT(*), 0)  AS pct_fora_banda,
          ROUND(AVG(aq), 1)                                    AS aq_medio
   FROM controle
   WHERE recebido_em >= datetime('now', 'localtime', '-10 minutes')
   GROUP BY modo;
   ```

   ```sql title="Último degrau (pico e tempo)"
   -- Último degrau de SUBIDA de cada controlador: sobressinal e tempo até a banda de 0,5 °C
   WITH m AS (
     SELECT id, recebido_em, modo, t, sp, LAG(sp) OVER (ORDER BY id) AS sp_ant FROM controle
   ),
   d AS (
     SELECT modo, MAX(id) AS id0 FROM m WHERE sp > sp_ant GROUP BY modo
   ),
   j AS (
     SELECT m.*, (SELECT recebido_em FROM m AS a WHERE a.id = d.id0) AS t0
     FROM m JOIN d ON m.modo = d.modo AND m.id >= d.id0
     WHERE m.sp = (SELECT sp FROM m AS b WHERE b.id = d.id0)
   )
   SELECT CASE modo WHEN 0 THEN 'PI Node-RED' WHEN 1 THEN 'ON/OFF interno'
                    WHEN 2 THEN 'PI interno' END AS controlador,
          MAX(sp) AS sp, COUNT(*) AS n,
          ROUND(MAX(t) - MAX(sp), 2) AS sobressinal,
          ROUND((julianday(MIN(CASE WHEN t >= sp - 0.5 THEN recebido_em END))
                 - julianday(MIN(t0))) * 86400, 0) AS s_ate_banda
   FROM j GROUP BY modo;
   ```

   A segunda consulta usa `LAG()` para achar a linha em que o SP **subiu**. A partir dela, mede o
   pico acima do SP e quanto tempo a temperatura levou para chegar a 0,5 °C dele.

## Referência rápida {/* #referencia */}

| Problema                                        | O que fazer                                                                                                                              |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Nós Modbus com "propriedades inválidas: Server" | no `modbus-client`, o _Serial port_ não pode ficar vazio, mesmo com _Type_ TCP: mude para Serial, preencha `/dev/ttyUSB`, volte para TCP |
