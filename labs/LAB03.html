Checklist — logs no ESP32 e ambientes de build (debug × release)​

  • Os cinco níveis de log (log_e … log_v) aparecendo no Wokwi com CORE_DEBUG_LEVEL=5 (T1)
  • O mesmo código com CORE_DEBUG_LEVEL=2, e a prova de que as mensagens saíram do binário (T2)
  • platformio.ini com dois ambientes, debug e release, compilando os dois (T3)
  • Logs com dados formatados, falhas, taxa de erro e hexdump, sem delay() (T4)
  • Firmware com relatório de boot, nos dois ambientes, com as evidências (T5)
  • Previsões P1–P3 respondidas no README.md
  • Nenhum push --force; cada tarefa num commit Tn:
  • Logout do Git e do gh no computador do laboratório
Pontuação

T1…T5 = 100 pts (esta aula não tem desafios): T1 15 · T2 20 · T3 20 · T4 20 · T5 25. O autograder normaliza para 0–10. Vale o commit Tn: mais recente de cada tarefa.

Até aqui, o firmware falava com você por Serial.println(). Funciona, mas não escala: um erro grave e um detalhe sem importância saem iguais, não se sabe de que arquivo veio cada linha, e os print de depuração ficam no produto, a não ser que alguém se lembre de apagá-los.

O core Arduino do ESP32 tem um sistema de log com cinco níveis. Cada mensagem sai com o instante, o nível, o arquivo, a linha e a função. E o mais importante: o nível é escolhido na compilação. As mensagens abaixo do nível escolhido não são escondidas, elas deixam de existir no firmware. Com dois ambientes no platformio.ini, o mesmo código vira um firmware de desenvolvimento, falante, e um de produto, que só registra erros.

Os labs seguintes usam os logs o tempo todo: o Lab 04 mostra, com eles, o que o Wi-Fi e o MQTT estão fazendo por dentro.

Objetivos​

  • Usar as macros log_e, log_w, log_i, log_d e log_v, com formatação estilo printf.
  • Entender o CORE_DEBUG_LEVEL: o filtro acontece na compilação, não na execução.
  • Provar que as mensagens filtradas saíram do binário.
  • Criar ambientes debug e release no platformio.ini e escolher qual compilar.
  • Usar o log para contar uma história: falha, recuperação, estatística e dump de bytes.

Material​

  • O ambiente dos Labs 01 e 02: Windows 11, VS Code no perfil ESP32IO com o terminal no Prompt de Comando (cmd), PlatformIO com o pio no Path e o Wokwi com licença ativa.
  • Nenhuma placa: tudo roda no Wokwi.

Como a correção funciona​

O autograder roda no GitHub a cada push. Para cada tarefa, ele acha o commit Tn: mais recente, volta o repositório àquele ponto e confere duas coisas: se o projeto compila (pio run) e se os requisitos da tarefa estão lá (as macros, o CORE_DEBUG_LEVEL pedido, os ambientes, as evidências). A nota de cada tarefa é proporcional às verificações que passam, e o resumo aparece na aba Actions do repositório.

Por isso cada tarefa é um commit: a T2 pede CORE_DEBUG_LEVEL=2 e a T3 volta a subir o nível. Sem o commit T2:, não haveria como corrigir a T2.

1.2 Ligar todos os níveis​

O nível de log é uma macro do pré-processador, passada ao compilador pelo build_flags:

platformio.ini
[env:esp32dev]
platform = espressif32@6.9.0
board = esp32dev
framework = arduino
monitor_speed = 115200
build_flags =
    -DCORE_DEBUG_LEVEL=5           ; 0 nada · 1 E · 2 W · 3 I · 4 D · 5 V
MacroNívelValorQuando usar
log_e()Error1falhas que impedem a operação (o sensor não responde)
log_w()Warning2algo estranho, mas o programa segue (valor fora da faixa)
log_i()Info3marcos normais ("Wi-Fi conectado")
log_d()Debug4detalhes úteis durante o desenvolvimento
log_v()Verbose5tudo, inclusive valores brutos e laços internos

Uma macro só gera código se o seu valor for menor ou igual ao CORE_DEBUG_LEVEL.

src/main.cpp (T1)
#include <Arduino.h>

#define LED_PIN 2

int chamadas = 0;                     // quantas vezes medir() rodou

int medir() {                         // uma "medida" com efeito colateral
  chamadas++;
  return 42;
}

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  Serial.println("=== Lab 03 - logs no ESP32 ===");

  log_e("Isto e um ERRO (log_e)");
  log_w("Isto e um AVISO (log_w)");
  log_i("Isto e uma INFO (log_i): LED no GPIO %d", LED_PIN);
  log_d("Isto e DEBUG (log_d): medida = %d", medir());
  log_v("Isto e VERBOSE (log_v)");

  Serial.printf("Nivel de log compilado = %d; medir() rodou %d vez(es)\r\n", ARDUHAL_LOG_LEVEL, chamadas);
}

void loop() {}

O ARDUHAL_LOG_LEVEL é o nível que o core realmente usou: o CORE_DEBUG_LEVEL, se ele foi definido, ou um padrão, se não foi (P1).

Parte 3 — Ambientes debug e release​

Trocar o nível na mão a cada build é fácil de esquecer. O PlatformIO permite vários ambientes ([env:nome]) no mesmo platformio.ini: o que for comum fica no [env], e cada ambiente acrescenta o que é dele.

platformio.ini
[platformio]
default_envs = debug              ; o "pio run" sem -e compila só este

[env]                             ; comum a todos os ambientes
platform = espressif32@6.9.0
board = esp32dev
framework = arduino
monitor_speed = 115200

[env:debug]                       ; desenvolvimento: logs até DEBUG
build_flags =
    -DCORE_DEBUG_LEVEL=4
    -DMODO_DEBUG

[env:release]                     ; produto: só os erros
build_flags =
    -DCORE_DEBUG_LEVEL=1

O default_envs fica na seção [platformio], e não no [env]: é uma opção do projeto, não do build. O -DMODO_DEBUG é uma macro sua, que o código pode testar:

src/main.cpp (no setup, logo depois do println do título)
#ifdef MODO_DEBUG
  Serial.printf("Firmware de DEBUG (CORE_DEBUG_LEVEL=%d)\r\n", CORE_DEBUG_LEVEL);
#else
  Serial.printf("Firmware de RELEASE (CORE_DEBUG_LEVEL=%d)\r\n", CORE_DEBUG_LEVEL);
#endif

Cada ambiente compila numa pasta própria, .pio\build\<ambiente>\. O Wokwi precisa saber qual delas rodar:

wokwi.toml
[wokwi]
version = 1
firmware = '.pio/build/debug/firmware.bin'
elf = '.pio/build/debug/firmware.elf'

Parte 4 — Logs com dados e falhas​

Um "sensor" simulado: uma leitura por segundo, que falha a cada quatro. Os níveis contam a história: o log_e marca a falha exata, o log_w mostra a recuperação, o log_i o funcionamento normal e o log_v o detalhe que só interessa às vezes. Tudo com millis(), sem delay() (Lab 02).

Acrescente ao main.cpp (antes do setup()):

src/main.cpp (T4)
#define LEITURA_MS 1000               // ms: uma leitura do "sensor" por segundo
#define LIMITE_C   30.0f              // acima disto, aviso

uint32_t leituras = 0, falhas = 0;
float ultimoValor = NAN;

bool lerSensor(float *saida) {
  static uint32_t tentativa = 0;
  tentativa++;
  if (tentativa % 4 == 0) {           // a cada 4 leituras, uma "falha"
    log_e("Falha ao ler o sensor (tentativa %lu)", (unsigned long)tentativa);
    return false;
  }
  *saida = 20.0f + (tentativa % 15);  // valor fake que varia de 20 a 34
  log_v("Sensor respondeu na tentativa %lu", (unsigned long)tentativa);
  return true;
}

void tarefaSensor() {
  float t;
  leituras++;
  if (lerSensor(&t)) {
    ultimoValor = t;
    if (t > LIMITE_C) log_w("Temperatura alta: %.1f C (limite %.0f)", t, LIMITE_C);
    else log_i("Temperatura: %.1f C", t);
  } else {
    falhas++;
    log_w("Leitura ignorada; ultimo valor valido: %.1f C", ultimoValor);
  }

  if (leituras % 10 == 0) {
    log_i("Taxa de falhas: %lu de %lu = %.1f%%", (unsigned long)falhas, (unsigned long)leituras,
          100.0f * falhas / leituras);
    // o "pacote" que iria pela rede: cabeçalho, temperatura em décimos, contadores, checksum
    uint16_t decimos = (uint16_t)(ultimoValor * 10);
    uint8_t pacote[8] = {0xA5, 0x03, (uint8_t)(decimos >> 8), (uint8_t)decimos,
                         (uint8_t)(leituras >> 8), (uint8_t)leituras, (uint8_t)falhas, 0};
    for (int i = 0; i < 7; i++) pacote[7] ^= pacote[i];
    log_buf_i(pacote, sizeof(pacote));
  }
}

unsigned long tLed = 0, tLeitura = 0;
bool ledAceso = false;

void loop() {
  unsigned long agora = millis();

  if (agora - tLed >= 500) {          // pisca, como no Lab 02
    tLed += 500;
    ledAceso = !ledAceso;
    digitalWrite(LED_PIN, ledAceso ? HIGH : LOW);
    log_v("LED %s", ledAceso ? "aceso" : "apagado");
  }

  if (agora - tLeitura >= LEITURA_MS) {
    tLeitura += LEITURA_MS;
    tarefaSensor();
  }
}

O log_buf_i imprime os bytes em hexadecimal e, depois do //, os que são texto (os outros viram .). Ele não tem o prefixo [I][arquivo:linha]. Confira o pacote: 0x01, 0x2c é 300, ou 30,0 °C em décimos; 0x00, 0x0a são 10 leituras; 0x02, 2 falhas.

Os log_v (o LED e o sensor que respondeu) não aparecem: o debug vai até o nível 4.

Preveja antes de rodar

P3: (a) a 115200 baud, cada caractere leva 10 bits na UART. Quanto tempo leva uma linha de log de 80 caracteres? O log_printf do core espera a UART terminar de enviar antes de voltar. O que aconteceria com um log_d dentro de um laço que precisa rodar a cada 1 ms? (b) Por que o pisca do LED usa log_v, e não log_d? (c) Por que o release mantém o nível 1, e não 0?

Projeto integrador — firmware com relatório de boot​

Todo firmware de produto deveria dizer, ao ligar, em que está rodando e por que reiniciou. Um reset por watchdog ou por queda de tensão é a primeira pista de um defeito no campo, e só aparece se o firmware registrar.

Requisitos​

  1. relatorioBoot(), chamado no fim do setup(), com:

    • modelo do chip, revisão, número de núcleos e frequência da CPU (log_i);
    • tamanho da flash e heap livre agora e o mínimo desde o boot (log_i);
    • versão do ESP-IDF por baixo do core Arduino (log_d);
    • motivo do último reset: log_i se foi o normal (ligar ou o botão EN), log_w se foi qualquer outro (watchdog, pânico, queda de tensão...).
    src/main.cpp (T5)
    #include <esp_system.h>              // esp_reset_reason()

    const char *nomeReset(esp_reset_reason_t r) {
      switch (r) {
        case ESP_RST_POWERON:  return "liga/desliga (POWERON)";
        case ESP_RST_EXT:      return "pino EN (EXT)";
        case ESP_RST_SW:       return "por software (SW)";
        case ESP_RST_PANIC:    return "panico/excecao (PANIC)";
        case ESP_RST_INT_WDT:  return "watchdog de interrupcao (INT_WDT)";
        case ESP_RST_TASK_WDT: return "watchdog de tarefa (TASK_WDT)";
        case ESP_RST_WDT:      return "outro watchdog (WDT)";
        case ESP_RST_BROWNOUT: return "queda de tensao (BROWNOUT)";
        case ESP_RST_DEEPSLEEP:return "saida do deep sleep (DEEPSLEEP)";
        default:               return "desconhecido";
      }
    }

    void relatorioBoot() {
      log_i("Chip %s rev %d, %d nucleo(s) a %lu MHz", ESP.getChipModel(), ESP.getChipRevision(),
            ESP.getChipCores(), (unsigned long)ESP.getCpuFreqMHz());
      log_i("Flash %lu KB", (unsigned long)(ESP.getFlashChipSize() / 1024));
      log_i("Heap livre %lu bytes (menor desde o boot: %lu)", (unsigned long)ESP.getFreeHeap(),
            (unsigned long)ESP.getMinFreeHeap());
      log_d("ESP-IDF %s", ESP.getSdkVersion());

      esp_reset_reason_t r = esp_reset_reason();
      if (r == ESP_RST_POWERON || r == ESP_RST_EXT) log_i("Reset: %s", nomeReset(r));
      else log_w("Reset inesperado: %s", nomeReset(r));
    }
