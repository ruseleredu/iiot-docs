Laboratório 02

Checklist — ambiente de desenvolvimento (parte 2): PlatformIO, Wokwi e Docker​

  • Extensões PlatformIO IDE e Wokwi Simulator no perfil ESP32IO, com o pio no Path (Parte 1)
  • Projeto PlatformIO na versão mais recente da plataforma (registrada na evidência), compilando, sem a .pio/ no repositório (T1)
  • Licença do Wokwi ativada, wokwi.toml + diagram.json e o pisca-LED simulado no VS Code (T2)
  • Pisca sem delay() (com millis()) e um breakpoint do GDB parando o firmware no Wokwi (T3)
  • Docker funcionando, Dockerfile + compose.yaml e o firmware compilado dentro do container (T4)
  • Firmware simulado pelo wokwi-cli no container, com teste automático do serial (T5)
  • Previsões P1–P3 respondidas no README.md
  • Nenhum token no repositório; nenhum push --force; cada tarefa num commit Tn:
  • Logout do Git e do gh no computador do laboratório
Pontuação

T1…T5 = 100 pts (esta aula não tem desafios): T1 15 · T2 20 · T3 15 · T4 20 · T5 30. O autograder normaliza para 0–10. Vale o commit Tn: mais recente de cada tarefa.

Antes de começar

Confira o ambiente (faça a configuração uma vez por máquina; a verificação, a cada aula):

  1. Instalar as ferramentas — git, GitHub CLI e VS Code
  2. Configurar o git — nome, e-mail e editor padrão (uma vez)
  3. Verificar git, gh e VS Code — deve mostrar as versões e Logged in to github.com

Verificação rápida de versão instalada:

git -v & gh --version & code -v & py --version & pio --version & wokwi-cli -V & wsl --version & docker --version

Verificação rápida de autenticação:

git config --get-regexp ^user\. & gh auth status & code --list-extensions --profile "ESP32IO"

O Git é a ferramenta de gerenciamento de código-fonte mais utilizada por desenvolvedores profissionais.

  • O Git é um sistema de controle de versão distribuído gratuito e de código aberto, projetado para lidar com tudo, desde projetos pequenos até muito grandes, com rapidez e eficiência.
winget install --id Git.Git -e --source winget

Configurações do git:

git config --list --show-origin

O GitHub CLI traz o GitHub para o seu terminal.

  • O GitHub CLI é uma ferramenta de linha de comando que permite interagir com o GitHub diretamente pelo terminal. Está disponível para Windows, macOS e Linux.
winget install --id GitHub.cli -e --source winget

Status de login do GitHub CLI:

gh auth status

O Python é uma linguagem de programação que permite trabalhar com rapidez e integrar sistemas de forma mais eficaz.

  • O Python pode ser instalado via winget:
winget install Python.Python.3.14

  • Verifique a versão instalada:

py --version && python --version && pip --version

  • Instale as dependências utilizadas no curso:

py -m pip install bcrypt

Visual Studio Code: IDE e Editor de Código para Desenvolvimento de Software.

  • O VS Code é um editor de código-fonte gratuito criado pela Microsoft para Windows, Linux e macOS. Inclui suporte para depuração, controle Git integrado, realce de sintaxe, conclusão inteligente de código, snippets e refatoração de código.
winget install --id Microsoft.VisualStudioCode -e --source winget

Extensões instaladas do Visual Studio Code para o perfil ESP32IO:

code --list-extensions --profile "ESP32IO"

Configurar o terminal do VS Code. No arquivo .vscode/settings.json

{
    "terminal.integrated.defaultProfile.windows": "Command Prompt"
}

PlatformIO IDE para VSCode: Sua porta de entrada para a excelência no desenvolvimento de software embarcado.

  • PlatformIO IDE para VSCode Desbloqueie o verdadeiro potencial do desenvolvimento de software embarcado com o ecossistema colaborativo do PlatformIO, adotando princípios declarativos, metodologias orientadas a testes e toolchains modernas para um sucesso incomparável.
    code --install-extension platformio.platformio-ide --profile "ESP32IO"

  • Torne o comando pio disponível no sistema:

    Você precisa editar a variável de ambiente do sistema chamada Path e adicionar o caminho %USERPROFILE%\.platformio\penv\Scripts\ no início da lista.

    %USERPROFILE%\.platformio\penv\Scripts\

  • Inicie o projeto no PlatformIO (Arduino):

    pio project init -b esp32dev -O "framework=arduino" -O "monitor_speed=115200" --ide vscode --sample-code

  • Inicie o projeto no PlatformIO (Espressif):

    pio project init -b esp32dev -O "framework=espidf" -O "monitor_speed=115200" --ide vscode --sample-code

  • System Prune:

    pio system prune -f

Wokwi para VSCode: Simulador de sistemas embarcados e IoT com suporte para ESP32.

  • Wokwi para VSCode executa a simulação dentro do VS Code, utilizando os binários compilados pelo PlatformIO.
code --install-extension wokwi.wokwi-vscode --profile "ESP32IO"
  • Gerar uma licença pessoal de 30 dias para o Wokwi VS Code.
  • Wokwi CLI: Baixe via GitHub.
curl -L -o "%USERPROFILE%\.platformio\penv\Scripts\wokwi-cli.exe" "https://github.com/wokwi/wokwi-cli/releases/latest/download/wokwi-cli-win-x64.exe"
wokwi-cli -h
  • Obtenha seu token em https://wokwi.com/dashboard/ci
setx WOKWI_CLI_TOKEN "wok_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
  • Wokwi para CI e GitHub Actions
  1. Conecte o ESP32 ao computador via USB.
  2. Abra o Gerenciador de Dispositivos (clique com o botão direito no Menu Iniciar → Gerenciador de Dispositivos).
  3. Expanda a seção Portas (COM e LPT).
  4. Procure por um dispositivo similar a:
    • Silicon Labs CP210x USB to UART Bridge (COMx)
    • Driver Windows CH340/CH341 USB para porta serial
    • FTDI ou “Dispositivo Serial USB (COMx)”

Anote o número da porta (ex: COM4, COM6, COM12). Se não aparecer nenhuma porta nova, o driver não está instalado. Baixe o driver correspondente (CP210x ou CH340) no site do fabricante da placa.

pip install esptool
esptool chip-id

Docker Desktop & WSL 2: O Docker Desktop no Windows 11 utiliza a arquitetura do WSL 2 para executar containers Linux nativamente com alta performance.

  • Habilitação e Atualização do WSL 2:

    wsl --install
    wsl --update && wsl --set-default-version 2

  • Instalação do Docker Desktop via Winget:

    winget install --id Docker.DockerDesktop -e

  • Confirme no terminal integrado do VS Code:

    wsl --version && docker --version && docker compose version

  • Teste de MQTT com mosquitto:

    docker run --rm eclipse-mosquitto:2 mosquitto_sub -h test.mosquitto.org -t "esp32iot/labtest"
    docker run --rm eclipse-mosquitto:2 mosquitto_pub -h test.mosquitto.org -t "esp32iot/labtest" -m "Hello from Docker!"

No Lab 01, o grupo passou a usar o Git e o GitHub. Agora entra o firmware: o PlatformIO compila o código do ESP32, e o Wokwi o roda num ESP32 simulado dentro do VS Code, com LED, monitor serial e depurador (GDB). E entra a última ferramenta do ambiente, o Docker: o mesmo build e a mesma simulação passam a rodar num container Linux, igual em qualquer computador, sem depender do que está instalado no Windows. É exatamente o que o CI do Lab 11 vai fazer a cada push. O MQTT fica para o Lab 04.

Objetivos​

  • Instalar o PlatformIO e o Wokwi no VS Code e fazer o primeiro build do ESP32.
  • Configurar um projeto PlatformIO e registrar a versão da plataforma que o build usou.
  • Ativar o Wokwi no VS Code e ligar o firmware do PlatformIO ao circuito (wokwi.toml, diagram.json).
  • Trocar o delay() por millis(), o padrão que todos os labs seguintes usam, e depurar o firmware simulado com o GDB.
  • Instalar o Docker, escrever um Dockerfile e um compose.yaml, e compilar e simular o firmware num container com o wokwi-cli.

Material​

  • O ambiente do Lab 01: Windows 11, VS Code, Git, gh, Python, e o terminal do VS Code no Prompt de Comando (cmd).
  • ~6 GB livres: o toolchain do ESP32 (~300 MB no Windows e de novo no container) e a imagem do Docker.
  • Uma conta no Wokwi (gratuita): a licença do simulador no VS Code e o token de CI do wokwi-cli.
  • Docker Desktop com WSL 2 (aba Docker da configuração do ambiente).
  • Nenhuma placa. A Parte 6 mostra como gravar uma placa real, para quem tiver.
Abas da configuração do ambiente usadas hoje

PlatformIO, Wokwi (extensão e licença), Docker (WSL 2 e Docker Desktop) e, só para quem tiver placa, Drivers. As demais já foram feitas no Lab 01. O wokwi-cli não precisa ser instalado no Windows: ele roda dentro do container.

Por que simular?

O Wokwi simula o ESP32 (incluindo o Wi-Fi), LEDs, potenciômetros, o DHT22, o display SSD1306 e um analisador lógico. Todo o semestre roda nele: ninguém depende da bancada, do cabo USB ou do driver da placa, e o mesmo circuito (diagram.json) vai para o repositório junto com o código. No Lab 11, o mesmo simulador roda sem interface, dentro do CI, com os mesmos comandos (pio run e wokwi-cli) que você roda hoje no container.

1.1 Instalar as extensões​

1.3 Versão da plataforma​

O pio project init escreve platform = espressif32, sem versão: o PlatformIO usa a versão mais recente da plataforma (e, com ela, do core Arduino e do toolchain). É o padrão desta disciplina, e vale também para as bibliotecas dos labs seguintes. O preço é que o mesmo código pode se comportar diferente quando sai uma versão nova; por isso a versão usada fica registrada na evidência do build (as linhas PLATFORM: e PACKAGES: no início do pio run). Para trazer a versão nova de algo já instalado: pio pkg update.

platformio.ini
[env:esp32dev]
platform = espressif32             ; sem versão: a mais recente
board = esp32dev
framework = arduino
monitor_speed = 115200             ; o mesmo valor do Serial.begin()

void piscar(uint8_t pino, uint16_t meioPeriodoMs);

void loop() {

Parte 3 — Pisca com millis() e depuração com GDB​

3.1 Sem delay()​

Com delay(500), o ESP32 fica parado meio segundo e não faz mais nada: não lê a serial, não atende o Wi-Fi, não confere um botão. Os labs seguintes fazem várias coisas "ao mesmo tempo", então o padrão é outro: o loop() gira o tempo todo e cada tarefa confere se já deu a hora.

src/main.cpp (T3)
#include <Arduino.h>

#define LED_PIN       2
#define MEIO_PERIODO  500              // ms aceso, ms apagado
#define RELATORIO_MS  2000             // a cada 2 s, uma linha no serial

unsigned long tLed = 0, tRelatorio = 0;
bool ledAceso = false;
uint32_t voltas = 0;                   // quantas vezes o loop() rodou

void setup() {
  Serial.begin(115200);
  pinMode(LED_PIN, OUTPUT);
  Serial.println("ESP32 inicializado! Lab 02, grupo X");
}

void loop() {
  unsigned long agora = millis();
  voltas++;

  if (agora - tLed >= MEIO_PERIODO) {          // já deu a hora de trocar o LED?
    tLed += MEIO_PERIODO;
    ledAceso = !ledAceso;
    digitalWrite(LED_PIN, ledAceso ? HIGH : LOW);
  }

  if (agora - tRelatorio >= RELATORIO_MS) {    // e a do relatório?
    tRelatorio += RELATORIO_MS;
    Serial.printf("[%7lu ms] LED %s · %lu voltas do loop() em 2 s\r\n",
                  agora, ledAceso ? "aceso " : "apagado", (unsigned long)voltas);
    voltas = 0;
  }
}

Evidência: pelo menos 5 linhas do monitor serial em evidencias/t3-serial.txt.

3.2 Depurar com GDB no Wokwi​

O Serial.printf mostra o que você mandou imprimir. O GDB para o firmware numa linha (breakpoint) e mostra todas as variáveis naquele instante, sem mudar o código. O Wokwi abre um servidor GDB na porta 3333, e o VS Code se conecta a ele.

  1. Extensão C/C++ (fornece o depurador cppdbg do VS Code):

    Terminal (cmd)
    code --install-extension ms-vscode.cpptools --profile "ESP32IO"

  2. wokwi.toml: acrescente a porta do servidor GDB.

    wokwi.toml
    [wokwi]
    version = 1
    firmware = '.pio/build/esp32dev/firmware.bin'
    elf = '.pio/build/esp32dev/firmware.elf'
    gdbServerPort = 3333

  3. .vscode/launch.json: diz ao VS Code qual GDB usar (o do toolchain do ESP32, baixado pelo PlatformIO), qual .elf tem os símbolos e onde está o servidor.

    .vscode/launch.json
    {
      "version": "0.2.0",
      "configurations": [
        {
          "name": "Wokwi GDB",
          "type": "cppdbg",
          "request": "launch",
          "program": "${workspaceFolder}/.pio/build/esp32dev/firmware.elf",
          "cwd": "${workspaceFolder}",
          "MIMode": "gdb",
          "miDebuggerPath": "${userHome}/.platformio/packages/toolchain-xtensa-esp32/bin/xtensa-esp32-elf-gdb.exe",
          "miDebuggerServerAddress": "localhost:3333"
        }
      ]
    }

    Confira que o GDB existe nesse caminho:

    Terminal do VS Code (cmd)
    dir "%USERPROFILE%\.platformio\packages\toolchain-xtensa-esp32\bin\*gdb*"

  4. Depurar. Compile (pio run), depois F1 → Wokwi: Start Simulator and Wait for Debugger: o simulador abre parado, esperando o GDB. Clique na margem à esquerda da linha ledAceso = !ledAceso; (aparece um ponto vermelho) e aperte F5 (configuração Wokwi GDB).

  5. O firmware para no breakpoint. No painel Run and Debug, a seção Variables mostra agora, e Watch aceita expressões (tLed, voltas, ledAceso). F5 continua até a próxima parada, F10 executa uma linha, F11 entra na função, Shift+F5 encerra.

Salve uma captura do VS Code parado no breakpoint, com as variáveis à vista, em evidencias/t3-gdb.png.

Variáveis optimized out

O build padrão do PlatformIO é otimizado (-Os): o compilador guarda variáveis em registradores ou as elimina, e o GDB mostra <optimized out>. Para depurar, acrescente build_type = debug ao [env:esp32dev] do platformio.ini e compile de novo; retire-o depois. Enquanto o firmware está parado no GDB, o tempo simulado também para: o millis() não avança, e o LED não troca (compare com o P1-b).

Parte 4 — Docker: o ambiente num container​

Até aqui, o build depende do seu Windows: da versão do PlatformIO, do Path, do perfil do VS Code. Um container é um Linux mínimo, descrito num arquivo de texto (Dockerfile), que roda igual em qualquer computador com Docker. Se o firmware compila no container, compila no computador do colega, no do professor e no CI.

PeçaO que é
Dockerfilea receita da imagem: sistema base + o que instalar (PlatformIO, wokwi-cli)
imagemo resultado do docker compose build: um "molde" pronto, guardado no Docker
containeruma execução da imagem; com --rm, é apagado quando o comando termina
compose.yamlcomo rodar: qual imagem, quais pastas montar, quais variáveis, qual comando de cada serviço
bind mounta pasta do repositório aparece dentro do container em /projeto: o que ele grava, você vê
volume nomeadouma pasta guardada pelo Docker entre execuções: aqui, o cache do PlatformIO (~300 MB)

4.1 Instalar e conferir o Docker​

Siga a aba Docker da configuração do ambiente: primeiro o WSL 2 (o wsl --install pede para reiniciar o computador), depois o Docker Desktop. Abra o Docker Desktop, aceite os termos e espere a baleia ficar parada na bandeja. Se ele reclamar de virtualização, ative-a na BIOS/UEFI (Intel VT-x ou AMD-V).

Confira no terminal do VS Code e grave a evidência:

Terminal do VS Code (cmd)
(wsl --version & docker --version & docker compose version & docker run --rm hello-world) > evidencias\t4-docker.txt 2>&1
type evidencias\t4-docker.txt

O hello-world baixa uma imagem minúscula, cria um container, imprime Hello from Docker! e o container é apagado (--rm). O wsl --version escreve em UTF-16, e por isso pode aparecer com espaços entre as letras no arquivo: tudo bem.

4.2 O Dockerfile​

Na raiz do repositório, crie o Dockerfile (sem extensão):

Dockerfile
# ELT85B - ambiente de build e simulação do ESP32 (os mesmos comandos do CI do Lab 11)
FROM python:3-slim

# curl: baixar o wokwi-cli · git: bibliotecas do PlatformIO vindas de repositórios
RUN apt-get update \
 && apt-get install -y --no-install-recommends curl ca-certificates git \
 && rm -rf /var/lib/apt/lists/*

RUN pip install --no-cache-dir platformio

# wokwi-cli: um único executável Linux, publicado no GitHub do Wokwi
RUN curl -fsSL -o /usr/local/bin/wokwi-cli \
      https://github.com/wokwi/wokwi-cli/releases/latest/download/wokwi-cli-linuxstatic-x64 \
 && chmod +x /usr/local/bin/wokwi-cli \
 && wokwi-cli --version

WORKDIR /projeto
CMD ["pio", "--version"]

Cada RUN vira uma camada da imagem. O Docker guarda as camadas em cache: se você mudar só a última linha, ele não instala o PlatformIO de novo. Por isso o que muda menos fica em cima. Sem versão no Dockerfile, o build pega o Python, o PlatformIO e o wokwi-cli mais recentes; para atualizar uma imagem já construída, use docker compose build --no-cache.

O contexto do build é a pasta inteira, enviada ao Docker antes de começar. O .dockerignore tira dele o que a imagem não usa (e o .env da T5, que nunca deve entrar numa imagem):

.dockerignore
.git
.pio
.vscode
evidencias
.env

4.3 O compose.yaml​

O docker compose guarda num arquivo os parâmetros que, com o docker run, você teria de digitar a cada vez. Os três serviços usam a mesma imagem; muda só o comando:

compose.yaml
# Configuração comum aos serviços (âncora YAML: &esp32 define, <<: *esp32 reutiliza)
x-esp32: &esp32
  build: .
  image: elt85b/esp32-dev:lab02
  working_dir: /projeto
  volumes:
    - .:/projeto # o repositório, dentro do container
    - platformio:/root/.platformio # cache do toolchain entre execuções
  environment:
    WOKWI_CLI_TOKEN: ${WOKWI_CLI_TOKEN:-} # vem do arquivo .env (T5), nunca do Git

services:
  pio: # compilar
    <<: *esp32
    command: pio run

  wokwi: # simular e testar o serial
    <<: *esp32
    command: >
      wokwi-cli --timeout 10000 --expect-text "voltas do loop"
      --serial-log-file evidencias/t5-serial.txt .

  ci: # compilar e simular, como o CI do Lab 11
    <<: *esp32
    command: sh -c "pio run && wokwi-cli --timeout 10000 --expect-text 'voltas do loop' ."

volumes:
  platformio:

  1. docker compose build monta a imagem a partir do Dockerfile (alguns minutos, na primeira vez).
  2. O primeiro docker compose run --rm pio baixa a plataforma espressif32 e o toolchain para Linux (~300 MB, de novo: o do Windows não serve no container) e guarda tudo no volume platformio.
  3. O segundo grava a evidência. O -T desliga o terminal interativo, que atrapalha quando a saída vai para um arquivo.

O firmware.bin aparece na sua pasta .pio/build/esp32dev/, porque o container escreve no bind mount. Projeto integrador — simular no container com o wokwi-cli​

O Wokwi do VS Code precisa de alguém olhando a tela. O wokwi-cli roda a mesma simulação sem interface: envia o firmware.bin e o diagram.json para o simulador do Wokwi (na nuvem), recebe o monitor serial e termina com um código de saída: 0 se o texto esperado apareceu no serial a tempo, diferente de 0 se não. É um teste automático do firmware, e é o que o CI do Lab 11 roda a cada push.

Requisitos​

  1. Token de CI. Em wokwi.com/dashboard/ci, entre com a sua conta e gere um token. Ele é pessoal: quem tem o token usa a sua cota de simulação.

  2. .env, fora do Git. Primeiro, garanta que o Git ignora o .env; depois, crie-o pelo VS Code (Explorer → novo arquivo .env):

    Terminal do VS Code (cmd)
    echo .env>> .gitignore
    git check-ignore -v .env
    .env (NÃO vai para o repositório)
    WOKWI_CLI_TOKEN=cole_aqui_o_seu_token

    O git check-ignore tem de responder .gitignore:N:.env .env. O docker compose lê o .env sozinho e passa o token ao container pelo ${WOKWI_CLI_TOKEN:-} do compose.yaml. Confira com git status: o .env não pode aparecer.

  3. Simular. Com o firmware da T3 já compilado (T4):

    Terminal do VS Code (cmd)
    docker compose run --rm wokwi
    echo %ERRORLEVEL%
    Saída (trecho; as mensagens do wokwi-cli variam com a versão)
    Wokwi CLI v0.x.x
    Starting simulation...
    ESP32 inicializado! Lab 02, grupo X
    [   2000 ms] LED aceso  · 1032915 voltas do loop() em 2 s
    Expected text found: "voltas do loop"
    TEST PASSED.
    0

    O --expect-text encerra a simulação assim que o texto aparece; o --timeout 10000 é o limite, em milissegundos simulados; o --serial-log-file grava o serial em evidencias/t5-serial.txt.

  4. Ver o teste falhar. Rode com um texto que o firmware nunca imprime (o comando depois do nome do serviço substitui o do compose.yaml):

    Terminal do VS Code (cmd)
    docker compose run --rm wokwi wokwi-cli --timeout 5000 --expect-text "texto que nunca aparece" .
    echo %ERRORLEVEL%

    O código de saída não é 0. É isso que faz o CI marcar o push em vermelho.

  5. Tudo de uma vez. O serviço ci compila e simula na sequência, como o Lab 11 fará:

    Terminal do VS Code (cmd)
    docker compose run --rm -T ci > evidencias\t5-wokwi.txt 2>&1
    echo exit=%ERRORLEVEL%>> evidencias\t5-wokwi.txt
    type evidencias\t5-wokwi.txt

    O echo fica numa linha separada de propósito: dentro de parênteses, o cmd trocaria o %ERRORLEVEL% pelo valor de antes do comando.

  6. Evidências: evidencias/t5-wokwi.txt (saída do serviço ci, terminando em exit=0) e evidencias/t5-serial.txt (gravado pelo serviço wokwi no passo 3).

  7. No README.md: as respostas de P1, P2 e P3.

Terminal do VS Code (cmd)
git status
git add .gitignore evidencias/t5-wokwi.txt evidencias/t5-serial.txt README.md
git commit -m "T5: firmware simulado no Docker com o wokwi-cli"

Parte 6 — Placa real (opcional)​

Quem tiver um ESP32 DevKit pode gravar o mesmo firmware: o código não muda.

Antes, siga a aba Drivers da configuração do ambiente: a placa tem de aparecer como uma porta COM no Gerenciador de Dispositivos, e o esptool chip-id tem de responder. Depois, no terminal do VS Code (a gravação é feita pelo Windows, não pelo container, que não enxerga as portas COM):

Terminal do VS Code (cmd)
pio device list
pio run -t upload
pio device monitor

O pio device list mostra as portas (COM3, COM4...). O upload compila e grava, e o monitor abre o serial a 115200 (Ctrl+C sai). Feche o monitor antes de gravar de novo: a porta COM só atende um programa por vez.
