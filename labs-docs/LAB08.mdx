Nos Labs 05 a 07, o ESP32 montou uma **câmara climática** (DHT22, OLED, potenciômetro,
aquecedor e ventilador) que falava **MQTT**, o protocolo típico de IoT.

Na indústria, quem conversa com o chão de fábrica são **CLPs**, **IHMs** e **SCADAs**, e eles
falam outros protocolos: **Modbus**, **S7** (Siemens) e **OPC-UA**. Nesta aula, a câmara vira
uma "máquina" industrial: o **`camara-sim`** é a mesma câmara, simulada num contêiner, que
expõe **a mesma planta** pelos quatro protocolos ao mesmo tempo.

O objetivo é entender **como cada protocolo organiza os dados** e **como o dado chega** ao
cliente. Por isso, o Node-RED faz só o mínimo: um nó que **lê** e mostra no _debug_, e um
_inject_ que **escreve**. Sem dashboard, sem banco, sem controle.

```mermaid
flowchart LR
  subgraph SIM["camara-sim · lab08-x-camara"]
    PL[Planta térmica<br/>T · UR · setpoint · aquecedor · ventilador]
  end
  PL ---|Modbus TCP · 502| NR[Node-RED<br/>ler → debug · inject → escrever]
  PL ---|S7 · 102 · DB1| NR
  PL ---|OPC-UA · 4840| NR
  PL -->|MQTT · telemetria| BRK[(mosquitto)] --> NR
```

## Os quatro protocolos em uma tabela

Guarde esta tabela: cada parte da aula preenche uma linha dela na prática.

|                          | **Modbus TCP**                                 | **S7**                                                       | **OPC-UA**                                   | **MQTT**                                       |
| ------------------------ | ---------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------- | ---------------------------------------------- |
| Origem                   | Modicon, 1979 (serial); aberto                 | Siemens; proprietário                                        | OPC Foundation; aberto (IEC 62541)           | IBM, 1999; aberto (OASIS)                      |
| Como o dado é endereçado | **número** do registrador (`IR0`, `HR3`)       | **bloco + byte** (`DB1,REAL20`)                              | **nó com nome** (`ns=2;s=Camara.temp`)       | **tópico** (`.../telemetria`)                  |
| Tipos                    | só bits e palavras de 16 bits                  | os do CLP (`BOOL`, `INT`, `REAL`…), mas o cliente é quem diz | o servidor **declara** o tipo de cada nó     | nenhum: o _payload_ é texto ou bytes           |
| O que é cada endereço    | um **mapa** em documento à parte               | uma **tabela de variáveis** à parte                          | o próprio servidor descreve (_browse_)       | combinado entre as partes                      |
| Como o dado chega        | **varredura**: o cliente pergunta a cada _x_ s | **varredura**                                                | **assinatura**: o servidor avisa quando muda | **publicação**: quem tem o dado envia          |
| Quem é servidor          | o equipamento (escravo)                        | o CLP                                                        | o equipamento                                | o **broker**; equipamento e SCADA são clientes |

## Objetivos

- Subir um **simulador de equipamento** em contêiner, ligado à rede do stack do curso.
- Entender o **modelo de dados** de cada protocolo: registradores (Modbus), blocos de dados com

## Parte 2 — Modbus TCP {/* #parte-2 */}

### 2.1 O modelo de dados do Modbus

O Modbus não tem nomes nem tipos: só **quatro tabelas** de endereços numerados, de bits ou de
palavras de 16 bits. O significado de cada endereço vem de um **mapa de registradores**, o
documento que o fabricante entrega com o equipamento. Este é o trecho do mapa da câmara que
vamos usar (unit 1, endereços a partir de 0):

| Tabela                | Função (FC)          | Acesso              | End.      | Variável                                                |
| --------------------- | -------------------- | ------------------- | --------- | ------------------------------------------------------- |
| **Coils**             | FC1 lê · FC5 escreve | bit, R/W            | 0         | `habilitado`                                            |
| **Discrete inputs**   | FC2                  | bit, só leitura     | 0–2       | LEDs verde, amarelo, vermelho                           |
| **Holding registers** | FC3 lê · FC6 escreve | 16 bits, R/W        | 3         | `setpoint` × 10 (350 = 35,0 °C)                         |
| **Input registers**   | FC4                  | 16 bits, só leitura | 0 / 1 / 2 | temperatura × 10 / umidade × 10 / setpoint efetivo × 10 |
|                       |                      |                     | 3 / 4     | aquecedor / ventilador (%)                              |

O mapa completo está no `camara-sim/README.md`.

:::note[Escala ×10]
Um registrador guarda só **inteiros** de 0 a 65535. Para ter uma casa decimal, o valor vai
**multiplicado por 10**: 35,2 °C viram `352`. Quem lê divide; quem escreve multiplica.
:::

### 2.2 Ler

Crie uma aba **Lab 08** no Node-RED e um nó de configuração **modbus-client**:

| Campo       | `câmara Modbus TCP`      |
| ----------- | ------------------------ |
| Type        | TCP                      |
| Host / Port | `lab08-x-camara` / `502` |
| TCP Type    | DEFAULT                  |
| Unit-Id     | `1`                      |

```mermaid
flowchart LR
  R[modbus-read · FC4 IR 0..4 · 2 s] --> D1[debug · registradores]
  R --> F[function · ÷10 e nomes] --> D2[debug · Modbus]
```

- **modbus-read** "FC4 IR 0..4": _FC 4: Read Input Registers_, Address `0`, Quantity `5`,
  Poll Rate `2 s`. A saída vai a um **debug** "Modbus (registradores)" e a uma function:

```js title="function: ÷10 e nomes"
// IR0..4 -> nomes e unidades (o mapa de registradores diz o que é cada um)
const r = msg.payload;
msg.payload = {
  temp: r[0] / 10, // IR0: °C x 10
  umid: r[1] / 10, // IR1: % x 10
  sp_efetivo: r[2] / 10, // IR2: °C x 10
  aquecedor: r[3], // IR3: %
  ventilador: r[4], // IR4: %
};
return msg;
```

- Ligue a function a um **debug** "Modbus" (_status_: `payload.temp`) e faça o **Deploy**.

```text title="Debug (o que chega do equipamento × o que ele significa)"
Modbus (registradores):  [ 362, 363, 350, 0, 20 ]
Modbus:                  { temp: 36.2, umid: 36.3, sp_efetivo: 35, aquecedor: 0, ventilador: 20 }
```

Sem o mapa, `[362, 363, 350, 0, 20]` são só números.

### 2.3 Escrever

| Nó                                   | Configuração                                                      |
| ------------------------------------ | ----------------------------------------------------------------- |
| inject "SP 30 °C" / "SP 40 °C"       | payload número `30` / `40`                                        |
| function "°C → HR3 (×10)"            | `msg.payload = Math.round(Number(msg.payload) * 10); return msg;` |
| modbus-write "FC6 HR3 setpoint"      | _FC 6: Preset Single Register_, Address `3`, Quantity `1`         |
| inject "Liga" / "Desliga"            | payload booleano `true` / `false`                                 |
| modbus-write "FC5 coil 0 habilitado" | _FC 5: Force Single Coil_, Address `0`, Quantity `1`              |

Clique "SP 40 °C": o `sp_efetivo` do debug vai a 40 e o aquecedor liga. Clique "Desliga": o
aquecedor vai a 0. Cada escrita aparece no log do simulador, com o protocolo de origem:

```shell title="Terminal (cmd)"
docker logs lab08-x-camara 2>&1 | findstr /l /c:"[cmd]"
```

```text title="Saída esperada (trecho)"
[15:45:03] [cmd] modbus: setpoint = 40.0
[15:45:08] [cmd] modbus coil: habilitado = False
[15:45:12] [cmd] modbus coil: habilitado = True
```

:::note[Dois conceitos que você vai encontrar em equipamentos reais]

- **Float32 em dois registradores:** para não perder precisão, muitos equipamentos guardam um
  `float` de 32 bits em **dois** registradores seguidos. A ordem das palavras (ABCD, CDAB…) muda
  de fabricante para fabricante, e errar a ordem dá números absurdos. A câmara faz isso nos
  IR12–13 (temperatura).
- **Modbus RTU:** o mesmo protocolo na linha serial **RS-485**, com o quadro endereço + função +
  dados + **CRC-16**. A câmara também responde em RTU (porta 5021, "RTU sobre TCP", como um
  conversor serial-Ethernet), mas não vamos usá-la hoje.
  :::

:::tip[Preveja antes de rodar]
**P1:** (a) o que acontece se você esquecer a function "×10" e mandar `37.5` direto para o HR3?
(Dica: o registrador só guarda inteiros, e o simulador limita o setpoint a 20…55 °C.) Teste e
confira no debug e no log. (b) O equipamento avisou algum erro? Por que não?
:::

**Evidência:** em `evidencias/t2-modbus.txt`, cole uma mensagem de cada debug ("registradores"
e "Modbus") e as linhas `[cmd]` do log.

## Parte 3 — S7: o DB1 {/* #parte-3 */}

### 3.1 O modelo de dados do S7

Num CLP Siemens, os dados do programa ficam em **blocos de dados** (DB). Um DB é uma sequência
de **bytes**, e cada variável é um **tipo** num **deslocamento** (_offset_): `REAL` (float) ocupa
4 bytes, `INT` 2 bytes, e um `BOOL` é **um bit** de um byte. O protocolo S7 (ISO-on-TCP,
porta 102) lê e escreve faixas desses bytes. O cliente precisa saber o **endereço** e o **tipo**
de cada variável.

| Endereço (nodes7) | Bytes           | Variável                          | Acesso |
| ----------------- | --------------- | --------------------------------- | ------ |
| `DB1,X0.0`        | bit 0 do byte 0 | `habilitado`                      | R/W    |
| `DB1,INT2`        | 2–3             | `modo`                            | R/W    |
| `DB1,REAL4`       | 4–7             | `setpoint` (°C)                   | R/W    |
| `DB1,REAL20`      | 20–23           | `temp` (°C)                       | R      |
| `DB1,REAL24`      | 24–27           | `umid` (%)                        | R      |
| `DB1,REAL28`      | 28–31           | `sp_efetivo` (°C)                 | R      |
| `DB1,INT40`       | 40–41           | `estado` (0 DESLIGADO … 4 ALARME) | R      |

Repare que **não há escala**: o `REAL` já é o valor em °C.

flowchart LR

## Parte 4 — OPC-UA: assinatura e escrita {/* #parte-4 */}

### 4.1 O modelo de dados do OPC-UA

No OPC-UA, o servidor publica um **espaço de endereçamento**: uma árvore de **nós**, cada um
com **nome**, **tipo**, **unidade** e permissões. O cliente não precisa de um mapa externo: ele
**navega** (_browse_) e descobre. Cada nó tem um **NodeId**. Na câmara:

```text title="Objects/Camara  (namespace urn:utfpr:camara-climatica = ns=2)"
Medicoes/    temp · umid                                  ns=2;s=Camara.temp ...
Atuadores/   aquecedor_pwm · ventilador_pwm
Estado/      estado · estado_txt · heartbeat · ...
Comandos/    habilitado · modo · setpoint · ...           (graváveis)
```

E o dado não precisa ser **perguntado** a cada 2 s. O cliente faz uma **assinatura**
(_subscription_): "me avise quando este nó mudar, verificando a cada 2 s".

:::info[Opcional: UaExpert]
No PC, conecte o UaExpert em `opc.tcp://localhost:4840/` (_Security_ None, anônimo). Navegue até
`Objects/Camara` e arraste `temp`, `setpoint` e `estado_txt` para o _Data Access View_. Repare
nos atributos de cada nó: `DataType`, `AccessLevel` e `Description`. Nenhum mapa foi preciso.
:::

### 4.2 Assinar e escrever no Node-RED

Crie um **OpcUa-Endpoint** "câmara OPC-UA": `opc.tcp://lab08-x-camara:4840/`, _Security
Policy_ None, _Mode_ None, anônimo.

```mermaid
flowchart LR
  I1[inject · topic ns=2;s=Camara.temp · once] --> C[OpcUa-Client · SUBSCRIBE · 2 s] --> D[debug OPC-UA]
  I2[inject · topic ns=2;s=Camara.setpoint · once] --> C
  I3[inject 35] --> IT[OpcUa-Item · Camara.setpoint · Double] --> W[OpcUa-Client · WRITE]
```

- Dois **inject** que disparam **uma vez** (_Inject once after_ 3 s), com o NodeId no **topic**:
  `ns=2;s=Camara.temp` e `ns=2;s=Camara.setpoint`. Cada mensagem cria uma assinatura.
- **OpcUa-Client** "assina (2 s)": _Action_ **SUBSCRIBE**, _Interval_ `2` s → **debug**
  "OPC-UA". Cada mudança chega numa mensagem, com o NodeId no `msg.topic` e o valor no
  `msg.payload`. A primeira mensagem (`topic: subscriptionId`) só informa o número da assinatura.
- Para escrever: inject `35` → **OpcUa-Item** (_Item_ `ns=2;s=Camara.setpoint`, _Type_ `Double`)
  → **OpcUa-Client** "escreve", _Action_ **WRITE**.

O tipo **tem** de bater com o do servidor: escrever um `Float` num nó `Double` é recusado com
`BadTypeMismatch`. Ao contrário do S7, o OPC-UA **sabe** o tipo e **avisa**.

:::

## Referência rápida {/* #referencia */}

| Protocolo  | Nó de configuração                                                        | Ler                                                          | Escrever                                                |
| ---------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------- |
| Modbus TCP | **modbus-client** `lab08-x-camara:502`, unit 1                            | **modbus-read** (FC1/2/3/4, endereço, quantidade, intervalo) | **modbus-write** (FC5 bobina, FC6 registrador)          |
| S7         | **s7 endpoint** `lab08-x-camara:102`, rack 0, slot 1, tabela de variáveis | **s7 in** (uma variável ou todas)                            | **s7 out** (uma variável)                               |
| OPC-UA     | **OpcUa-Endpoint** `opc.tcp://lab08-x-camara:4840/`                       | **OpcUa-Client** READ ou SUBSCRIBE, NodeId no `msg.topic`    | **OpcUa-Item** (NodeId + tipo) → **OpcUa-Client** WRITE |
| MQTT       | **mqtt-broker** `mosquitto:1883`                                          | **mqtt in** (tópico)                                         | **mqtt out** (tópico)                                   |

| Problema                                        | O que fazer                                                                                                                                                             |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Nó Modbus/S7/OPC-UA "desconectado"              | o simulador está na rede do stack? `docker logs lab08-x-camara`; no Node-RED, o host é `lab08-x-camara`, e não `localhost`                                              |
| Nós Modbus com "propriedades inválidas: Server" | no `modbus-client`, o campo _Serial port_ não pode ficar vazio, mesmo com _Type_ TCP: mude o _Type_ para Serial, preencha `/dev/ttyUSB`, volte para TCP e faça o Deploy |
| `port is already allocated` no `up`             | troque a porta do lado do PC no `.env`                                                                                                                                  |
| Setpoint "errado" pelo Modbus                   | faltou o ×10 (P1)                                                                                                                                                       |
| Valores sem sentido no S7                       | endereço ou tipo errado na tabela de variáveis (P2)                                                                                                                     |
| `BadTypeMismatch` no OPC-UA                     | o _Type_ do OpcUa-Item tem de ser o do nó (`Double` para o setpoint)                                                                                                    |
| Nada chega no debug "MQTT"                      | o tópico tem de ser **idêntico** ao `MQTT_BASE` do `.env`, mais `/telemetria`                                                                                           |
| Parar o simulador                               | na pasta `camara-sim`: `docker compose -f docker-compose.yml -f docker-compose.lab.yml down`                                                                            |
