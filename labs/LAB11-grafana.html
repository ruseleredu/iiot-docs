Laboratório 11 (Grafana)

Checklist — histórico e análise da câmara com Grafana​

  • Tabela leituras (tempo em ms, UTC) gravada pelo Node-RED a cada ~2 s (T1)
  • Grafana no ar, na rede do LAB IoT, com a fonte de dados SQLite testada (T2)
  • Painel "Câmara climática": série T × SP × aquecedor, valor atual, umidade e linha do tempo do estado (T3)
  • Análise: comparação dos controladores, anotações das trocas de modo e médias por minuto (T4)
  • Alerta do Grafana → Node-RED → MQTT e ntfy, testado com a câmara quente (T5)
  • Previsões P1–P4 respondidas no README.md
  • Nenhum push --force; cada tarefa num commit Tn:
Pontuação

T1…T5 = 100 pts (esta aula não tem desafios): T1 15 · T2 15 · T3 25 · T4 20 · T5 25. O autograder normaliza para 0–10. Vale o commit Tn: mais recente de cada tarefa.

A câmara já tem quem a controle (o PI interno ou o do Node-RED, Lab 09) e quem a opere (o FUXA, Lab 10). Falta quem olhe para trás: o engenheiro de processo que quer saber como a câmara se comportou ontem, qual controlador gasta menos aquecedor, quantas vezes ela passou do limite e quando isso aconteceu.

Esse é o papel do Grafana: ler o histórico guardado num banco e transformá-lo em painéis, comparações e alertas. Ele não escreve na câmara. É uma ferramenta de análise, não de operação.

Objetivos​

  • Guardar uma série temporal com o tempo em formato adequado (ms desde 1970, UTC).
  • Subir o Grafana em contêiner, com a fonte de dados e os painéis provisionados por arquivo.
  • Montar um painel com séries, valor atual, medidor e linha do tempo de estados.
  • Escrever SQL de análise: agregação por controlador, detecção de trocas (LAG) e médias por minuto (downsampling).
  • Criar uma regra de alerta e entregá-la ao Node-RED por webhook.

Material​

  • O LAB IoT do lab11-x (gen_iot_aluno.py), a câmara (camara-sim/) e o fluxo do Lab 10 (nodered/flows-lab10.json).
  • A pasta grafana/ do repositório: docker-compose.yml, .env.example e provisioning/.
  • Acesso à internet no primeiro up: a imagem do Grafana e o plugin SQLite são baixados.
Por que SQLite, e não um banco de séries temporais?

Numa planta real, o histórico iria para um banco feito para séries temporais (InfluxDB, TimescaleDB, Prometheus) e o Grafana leria de lá. Aqui, o SQLite do Node-RED já existe desde o Lab 09 e o plugin frser-sqlite-datasource permite lê-lo direto. O SQL e os painéis são os mesmos que você usaria com outro banco.

1.2 Uma tabela para séries temporais​

A tabela controle do Lab 09 guarda o instante como texto na hora local (2026-10-22 14:05:31.270). Serve para uma consulta, mas atrapalha uma ferramenta de séries temporais: o texto depende do fuso do contêiner, se repete na volta do horário de verão e precisa ser convertido a cada consulta. A nova tabela guarda o instante como número: os milissegundos desde 1970 em UTC, exatamente o que o Date.now() devolve.

Node-REDConfiguração
inject "Criar tabela leituras"once após 1 s; o SQL abaixo no topic
sqlite "esquema (batch)"SQL Query Batch without response (executa vários comandos de uma vez)
topic do inject 'Criar tabela leituras'
CREATE TABLE IF NOT EXISTS leituras (
    ts      INTEGER NOT NULL,  -- instante em ms desde 1970-01-01 (UTC), como o Date.now()
    temp    REAL,              -- °C
    umid    REAL,              -- %
    sp      REAL,              -- setpoint efetivo (°C)
    aq      REAL,              -- % aquecedor aplicado
    ve      REAL,              -- % ventilador aplicado
    modo    INTEGER,           -- 0 MANUAL, 1 ON/OFF, 2 PI interno
    estado  TEXT               -- DESLIGADO, AQUECENDO, RESFRIANDO, ESTAVEL, ALARME
);
CREATE INDEX IF NOT EXISTS leituras_ts ON leituras (ts);

O índice em ts deixa rápidas as consultas por intervalo de tempo, que são todas as do Grafana.

Ligue a saída do "junta variáveis" (Lab 09, T4) a uma function e a um sqlite em Prepared Statement:

function: monta leitura
// Cada conjunto do OPC-UA -> uma linha em 'leituras' (ts em ms, UTC)
const p = msg.payload;
if (typeof p.temp !== "number") return null;
msg.params = {
  $ts: Date.now(),
  $temp: p.temp,
  $umid: p.umid,
  $sp: p.sp_efetivo,
  $aq: p.aquecedor_pwm,
  $ve: p.ventilador_pwm,
  $modo: p.modo,
  $estado: p.estado_txt,
};
return msg;
sqlite 'INSERT leituras' (Prepared Statement)
INSERT INTO leituras (ts, temp, umid, sp, aq, ve, modo, estado)
VALUES ($ts, $temp, $umid, $sp, $aq, $ve, $modo, $estado);

4.1 Comparar os controladores​

Um painel Table com a comparação do Lab 09, agora sobre o intervalo da tela:

consulta 'comparar'
SELECT CASE modo WHEN 0 THEN 'PI Node-RED' WHEN 1 THEN 'ON/OFF interno'
                 WHEN 2 THEN 'PI interno' END        AS controlador,
       COUNT(*)                                          AS amostras,
       ROUND(AVG(ABS(sp - temp)), 2)                     AS erro_medio,
       ROUND(100.0 * SUM(ABS(sp - temp) > 0.5) / COUNT(*), 0) AS pct_fora_banda,
       ROUND(AVG(aq), 1)                                 AS aq_medio
FROM leituras
WHERE ts BETWEEN $__from AND $__to
GROUP BY modo
ORDER BY modo;

4.2 Anotações: quando o modo mudou​

Uma anotação é uma marca vertical sobre todos os gráficos do painel. Em Dashboard settings ▸ Annotations ▸ New, fonte Camara (SQLite), com a consulta abaixo. O LAG() (Lab 09) compara cada linha com a anterior e só devolve as linhas em que o modo trocou:

anotação 'trocas de modo'
SELECT ts / 1000.0 AS time,
       'modo ' || ant || ' -> ' || modo AS text
FROM (SELECT ts, modo, LAG(modo) OVER (ORDER BY ts) AS ant
      FROM leituras
      WHERE ts BETWEEN $__from AND $__to)
WHERE ant IS NOT NULL AND modo <> ant
ORDER BY ts;
Resultado (exemplo)

4.3 Médias por minuto​

Um Time series "Temperatura por minuto" que agrega antes de desenhar: uma linha por minuto, com a média, o mínimo e o máximo.

consulta 'minuto'
SELECT (ts / 60000) * 60 AS time,
       ROUND(AVG(temp), 2) AS "T média",
       MIN(temp)           AS "T mín",
       MAX(temp)           AS "T máx"
FROM leituras
WHERE ts BETWEEN $__from AND $__to
GROUP BY ts / 60000
ORDER BY time;

Como ts é inteiro, ts / 60000 é a divisão inteira: todas as leituras do mesmo minuto caem no mesmo grupo.

Projeto integrador — alerta do Grafana no Node-RED​

O FUXA (Lab 10) tem alarmes para o operador, na tela, a cada segundo. O Grafana tem alertas para quem não está olhando: avaliam o histórico de tempos em tempos e avisam por fora (e-mail, chat, webhook). Aqui, o aviso vai para o Node-RED, que o republica no MQTT e no ntfy do LAB IoT (o celular do grupo).

Requisitos​

  1. Node-RED: receber o webhook. Um http in POST /alerta, ligado a um http response (código 200) e a esta function:

    function: alerta do Grafana
    // Webhook do Grafana (contact point): status firing/resolved e a lista de alertas
    const g = msg.payload || {};
    const a = (g.alerts || [])[0] || {};
    const nome = (a.labels && a.labels.alertname) || "Grafana";
    const disparou = g.status === "firing";
    msg.topic = (disparou ? "ALERTA: " : "Normalizado: ") + nome;
    msg.payload = {
      status: g.status,
      alerta: nome,
      resumo: (a.annotations && a.annotations.summary) || g.title || "",
      valor: a.valueString || "",
      desde: a.startsAt || "",
    };
    node.status({
      fill: disparou ? "red" : "green",
      shape: "dot",
      text: msg.topic,
    });
    return msg;

    function: aviso no ntfy (seguida de um http request, método 'set by msg.method')
    // Alerta -> ntfy do LAB IoT (as variáveis NTFY_* já estão no contêiner do Node-RED)
    msg.url = env.get("NTFY_URL");
    msg.method = "POST";
    msg.headers = {
      Authorization: "Bearer " + env.get("NTFY_TOKEN"),
      "Content-Type": "application/json",
    };
    msg.payload = {
      topic: env.get("NTFY_TOPIC"),
      title: msg.topic,
      message:
        msg.payload.resumo +
        (msg.payload.valor ? " (" + msg.payload.valor + ")" : ""),
      priority: msg.payload.status === "firing" ? 4 : 2,
      tags: [msg.payload.status === "firing" ? "warning" : "white_check_mark"],
    };
    return msg;
